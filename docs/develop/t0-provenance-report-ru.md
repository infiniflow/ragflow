# T0: происхождение кода и сохраняемые возможности

Дата: 2026-09-05. T0 выполнен для снимка в `tools/quality/file-inventory.json`: точные HEAD, время, staged/unstaged/untracked, SHA-256 файлов и счётчики находятся в нём. Это инвентаризация происхождения, а не подтверждение работоспособности приложения или отсутствия мёртвого кода. T1 завершён как baseline с известными сбоями; T2 выполняется, T3–T7 не завершены.

## Подтверждённая база

База содержимого: `cb93883f3f8c975eecb2fed81210effeb3bdb06f`, дерево `24f48284fedd4d7be28380953ff65b58261397c3`, версия проекта в этой точке `0.26.4`. Официальный GitHub подтвердил SHA коммита, дерево и исходного родителя `2b95fa2ba4510b4e89770c9551a0909661da549a`. Подтверждённого release tag нет; поле оставлено `null`. [Официальный commit](https://github.com/infiniflow/ragflow/commit/cb93883f3f8c975eecb2fed81210effeb3bdb06f).

Локальный репозиторий shallow на этой границе. Более раннюю историю локально не исследовать без её загрузки. Remote-tracking refs записаны как локальные наблюдения: `fetch` не выполнялся, их актуальность на сервере не утверждается.

**Риск UPG-01:** графовый `merge-base HEAD upstream/main` возвращает `28ce77fe5f1e4301d3672221b509418d3c7acb77`, но merge `64f0bfdf0e724d006d61563a76964bf140bcfb4e` имеет то же дерево `bcc60fea39d9f27034943c3001bc226e6c10b518`, что и первый родитель `268a5a9d60e19982ac329ec045d0ff9b0228b26b`. Его diff относительно первого родителя пуст. Это доказательство присоединения истории без изменения содержимого в данном merge, а не доказательство принятия всех изменений второго родителя. Конкретная стратегия слияния по этому факту не устанавливается.

Для следующего upstream update требуется отдельно проверить отсутствующее содержимое уже включённых в историю коммитов: Git учитывает их ancestry и не воспроизведёт автоматически все прежние изменения. Базу нельзя просто заменить августовским SHA. Обновление выполняется отдельной задачей из полного committed snapshot с проверками миграций и восстановления; T0 не меняет историю.

## Что учтено

- Все пути, отличающиеся от подтверждённой базы в HEAD, индексе или рабочем дереве, и неигнорируемые untracked-файлы.
- Для каждого пути: один основной владелец области, происхождение `core_change` либо `extension`, Git blobs базы/HEAD/индекса и SHA-256 фактических байтов рабочего файла. Принадлежность к стандартному дереву устанавливается по Git tree, не по имени каталога. Rename сохраняется как delete/add, включая удалённый путь.
- Неизменённые upstream-пути учитываются отдельно по точному равенству; они не становятся кандидатами на удаление из-за выбранного runtime-профиля.
- Все first-parent коммиты форка после базы и их пофайловые изменения сохранены в `upstream-evidence.json`. Широкие исторические исправления TypeScript/UI выделены отдельно: происхождение известно, необходимость каждого hunk требует T1/ревью.
- Генерируемые `file-inventory.json` и `core-changes.yaml` перечислены, но не хешируют сами себя. Снимок проверяет изменение статуса, HEAD, содержимого файлов и индекса во время чтения; это обнаружение конкурирующих правок, не блокировка рабочего дерева после возврата команды.

При первоначальном выполнении T0 HEAD изменялся извне: исходно `3cf71a547e2a7610da908163a19a0e2d595e01c8`, промежуточно `768cec9866e4b1c84cbd71b7d8918db567a6d252`, затем `80a6711882b09923504768b492bcaefc61664691`. Перед выпуском снимок повторно собран по фактическому HEAD `5100b7e3b2720f968b071b28d336e4dcae2e940d` и текущему рабочему дереву. Старые числа не используются как итог.

В снимке завершения T0: 589 классифицированных путей, из них 327 `core_change` и 262 `extension`; 4 114 upstream-путей не затронуты. От базы до того HEAD — 546 изменённых путей; в рабочем дереве отдельно учтены 69 unstaged и 15 untracked путей. Эти множества пересекаются и не складываются как независимые. Это исторические числа T0: актуальные HEAD, fingerprint и количества после продолжения T1 находятся в `file-inventory.json`, а результаты поведения — в [отчёте T1](t1-regression-report-ru.md).

Это пофайловая классификация T0; symbol-level границы и проверка импортов относятся к T2.

## Игнорируемые ресурсы

`ignored-artifacts.json` отдельно фиксирует untracked ignored-файлы в `deployment/linux-pg`, `agent/business_requirements` и `services/asr-online-service`. Исключённые зависимости, caches и uploads перечислены явно. Это ограниченный обзор корней расширений и поставки, не полная инвентаризация диска или резервная копия БД/MinIO.

Найдены игнорируемые исходники диаграмм `document_constructor_*.puml` и выпускные архивы. Для небольших исходников сохранён SHA-256; для архивов, runtime-результатов и локальной конфигурации — только метаданные, без чтения содержимого. Новое правило `/deployment/linux-pg` не исключает уже tracked-файлы из основного снимка, но будущие untracked-файлы под ним Git не защитит. Перед переносом/выпуском надо отдельно решить, какие исходники включать в Git, а какие артефакты сохранять в хранилище выпусков. T0 не меняет `.gitignore`.

## Повторение и проверки

Из корня репозитория в PowerShell:

```powershell
.venv\Scripts\python.exe tools/quality/capture_inventory.py
.venv\Scripts\python.exe tools/quality/capture_inventory.py --write
.venv\Scripts\python.exe test/unit_test/tools/quality/test_capture_inventory.py
ruff check tools/quality/capture_inventory.py test/unit_test/tools/quality/test_capture_inventory.py
ruff format --check tools/quality/capture_inventory.py test/unit_test/tools/quality/test_capture_inventory.py
```

Первая команда проверяет текущую полноту и печатает новый fingerprint без записи; она не сравнивает его автоматически с сохранённым. `--write` обновляет только два генерируемых реестра. При новом/удалённом пути сначала предметно обновить точные записи `module-map.yaml`; неизвестные и лишние записи завершают команду ошибкой. Изменение базы требует повторного подтверждения upstream и обновления evidence. История в `upstream-evidence.json` и обзор ignored-файлов имеют собственный момент фиксации; capture не освежает их автоматически после нового commit или генерации артефактов. Нужны Git, Python и PyYAML; отсутствие зависимости является ошибкой.

Проверки утилиты выполняются в временных Git-репозиториях: staged/unstaged/untracked, delete/add rename, tracked под ignore, неизвестный путь, подмена дерева базы, отсутствие записи при чтении и конкурентные изменения файла/индекса. Команды приложения, live suites и миграции в T0 не запускались. Первоначальная отметка `NOT_RUN_IN_T0` не означала PASS; после прогонов T1 карта ссылается на отдельные результаты и ограничения. Пустой `baseline.json` не создавался.

Результат проверки реализации T0: 8 unittest-тестов — PASS; `ruff check` и `ruff format --check` двух Python-файлов — PASS. Контроль ссылок реестров и повторное чтение snapshot выполняются отдельно от тестов поведения приложения.

Проверка чистоты изменения: утилита имеет один путь сбора через `capture`, CLI и тесты используют его; приложение не импортируется. Алгоритм линеен по числу путей и размеру читаемого содержимого; повторное чтение затронутых файлов нужно для обнаружения конкурентных правок. Автоматический анализ достижимости/сложности приложения остаётся T2, массовые удаления не выполнялись.

Следующий этап — продолжение T2: расширить report-only анализ на оставшиеся критичные runtime roots и registrations, затем добавить широкий TypeScript/Go анализ до включения T3 CI gate.
