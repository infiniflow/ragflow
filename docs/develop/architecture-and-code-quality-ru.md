# Архитектура расширений RAGFlow, обновления upstream и качество кода

Статус: проект целевой архитектуры. Дата: 2026-09-05.
Основание: рабочее дерево `S:\ragflow`, HEAD `dd5cdfdc5`, включая локальные изменения.
Документ задаёт направление развития; полные ограничения импортов и проверки CI ещё не внедрены. Реестры происхождения T0 созданы позднее для снимка из [отчёта инвентаризации](t0-provenance-report-ru.md), а T2 имеет report-only Python-проверки ARC-01/02 static slices и прямых reverse consumers, две изолированные runtime-пробы Business Documents, exact Canvas DSL contracts для локального OpenMetadata component и изменённого Retrieval tool, а также focused adapter contracts. Приоритет — сохранение собственных доработок при регулярных обновлениях из `infiniflow/ragflow`.

Практическое внедрение описано в [плане перехода](architecture-transition-ru.md): этапы T0–T7, критерии завершения и инструкции разработчику, агенту и ревьюеру. [Каталог правил и проверок](architecture-checks-ru.md) задаёт rule IDs, матрицу запуска, форматы реестров, результаты CI и приёмочные пробы. Архитектурные решения принадлежат этому документу, последовательность работ — плану, исполняемые критерии — каталогу; связанные инструкции ссылаются на них вместо копирования полных правил.

## 1. Архитектурное решение

Развивать проект как **сопровождаемый форк RAGFlow с изолированными собственными модулями и минимальными изменениями стандартного ядра**. Сохранить структуру каталогов, runtime и способы сборки upstream. Строгое разделение domain/application/adapters применять внутри собственных возможностей. API, CLI, MCP и воркеры вызывают единый сценарий своего модуля.

Обновляемость означает сохранение функций и данных после контролируемого слияния и проверки. Она не гарантирует отсутствие конфликтов Git или изменений интеграционных адаптеров. Даже обновление только стандартных файлов может изменить поведение, схему БД или контракт, от которого зависит расширение.

Единица архитектуры — модуль с владельцем данных, публичным контрактом и проверяемыми зависимостями. Каталог, процесс и сервис развёртывания — разные понятия. Вынос в отдельный сервис оправдан независимым масштабированием, ресурсной изоляцией или отдельным жизненным циклом; количество папок само по себе этого не требует.

Python и Go сохраняют назначение в выбранном upstream-релизе. Не переносить стандартную функциональность между языками ради локального архитектурного единообразия. Для собственной возможности в конкретном профиле развёртывания назначается ровно один исполнитель и владелец записи. Стандартные альтернативные runtime не удаляются только потому, что один из них сейчас не включён локально.

Основные решения:

1. Стандартные корни `api`, `rag`, `agent`, `internal`, `web` не перестраиваются массово.
2. Собственная бизнес-логика живёт в принадлежащих форку модулях, не распределяется по общим upstream-services.
3. Связь расширения с ядром проходит через узкие адаптеры и явно учтённые точки регистрации. Новый plugin framework ради этого не создаётся.
4. Изменение стандартного файла имеет причину, владельца, тест и проверку необходимости при следующем обновлении.
5. Правила архитектуры и удаления лишнего кода обязательны для собственных модулей; ядро проверяется без принудительного переписывания под локальную модель слоёв.
6. Каждый upstream-релиз сначала интегрируется и проверяется отдельно от рабочей поставки, включая миграции собственных данных.

### 1.1 Три области ответственности

| Область | Что относится | Политика изменений |
| --- | --- | --- |
| Стандартное ядро | Код выбранного upstream commit | Сохранять его структуру; необходимые исправления локализовать и по возможности предлагать upstream |
| Собственные расширения | Бизнес-документы, собственные интеграции и другие подтверждённые доработки | Полный контроль архитектуры, тестов и удаления лишнего кода |
| Изменения на границе | Регистрация маршрутов/компонентов, модели и миграции, UI navigation, запуск worker, настройки сборки | Минимальный осмысленный diff, контрактные тесты, учёт в реестре изменений ядра |

Принадлежность определяется сравнением с зафиксированным upstream commit и историей изменения, а не названием каталога. Файл ядра может содержать собственный участок; новая папка внутри `api` не становится стандартной автоматически. Известные дефекты ядра разбираются и исправляются по необходимости; минимизация diff не оправдывает сохранение воспроизведённой ошибки.

## 3. Карта модулей и владение данными

Названия ниже обозначают логические ответственности, а не план переименования или выделения всех стандартных модулей. Существующие возможности ядра используются через его действующие сервисы. Физически разделяются только собственные модули по мере необходимости.

| Модуль | Ответственность и принадлежащие данные | Допустимые обращения |
| --- | --- | --- |
| `identity` | Tenant, пользователь, членство, аутентификация | Базовые технические средства |
| `knowledge` | Наборы данных, документы, метаданные, состояние жизненного цикла; политики доступа к ним | identity, files |
| `files` | Объект, размер, MIME, контрольная сумма, состояние загрузки и удаления | identity, object storage |
| `ingestion` | Задания обработки, попытки, прогресс, публикация результата | knowledge, files, models, parsing, retrieval indexing |
| `retrieval` | Индексирование проекций, фильтрация, поиск, ранжирование, ссылки на источники | knowledge для области доступа; модели embedding/reranking |
| `conversation` | Диалог, сообщения, генерация ответа и цитаты | identity, retrieval, models |
| `workflow` | DSL, запуск, шаги, checkpoint, cancel/resume | Узкие порты tools; алгоритмы canvas |
| `business_documents` | Документ, ревизии, предложения, согласование, доказательства, экспорт; собственные политики доступа | identity, retrieval, files, models |
| `models` | Настройки провайдеров, выбор модели, лимиты и учёт использования | identity, адаптеры LLM/embedding/ASR/TTS |
| `connectors` | Настройки источника, курсор синхронизации, расписание | files, knowledge, ingestion |
| `memory` | Сохранённая память и её жизненный цикл | identity, models, retrieval по явно выделенному контракту |
| `audit` | Неизменяемые записи значимых действий | Получает события через порт; не управляет бизнес-модулями |

Матрица определяет взаимодействия собственных модулей с нужными возможностями. Она не навязывает новый граф импортов стандартному ядру. Domain/application расширения не обращаются к чужим ORM-моделям. Адаптер использует действующий сервис ядра; если отдельного контракта нет и необходима работа с ORM, она локализуется в адаптере, документируется и тестируется на конкретной upstream-версии.

Политика доступа к ресурсу принадлежит владельцу ресурса. `identity` предоставляет проверенную личность и членство, но не становится универсальным сервисом бизнес-разрешений. В частности, knowledge проверяет доступ к dataset, business_documents — к ревизии и операции согласования.

При цикле A → B → A сначала разделить команду и уведомление либо передать необходимые факты в запросе. Общий технический интерфейс извлекается только при наличии самостоятельного смысла; перенос обеих сторон в `common` цикл не исправляет.

## 4. Структура с сохранением upstream

Сохранять существующие места размещения собственных функций, если они уже изолированы. Не вводить общий перенос в `api/modules`, `web/src/features`, `web/src/shared` и не перекраивать `internal/service`/`internal/entity`. Сначала убрать смешение обязанностей внутри своего модуля; смена адреса пакета сама по себе обновляемость не улучшает.

```text
api/                          # стандартная структура upstream
  apps/
    business_documents/
      domain/                 # состояния, инварианты, правила переходов
      application/            # команды, запросы, порты I/O
      adapters/               # собственное хранение и обращения к ядру
      worker.py               # вход в тот же application
  db/                         # структура ядра; учёт собственных точек регистрации
agent/
  business_requirements/      # существующие contracts/prompts/policies/templates
rag/                          # сохраняется upstream-структура
deepdoc/                      # сохраняется upstream-структура
common/                       # не пополняется собственной бизнес-логикой
cmd/                          # точки входа выбранного upstream-релиза
internal/                     # сохраняется upstream-структура Go
web/src/
  pages/business-documents/   # собственный экран, компоненты, model/types
  services/
    business-document-service.ts  # существующий клиент API функции
  routes.tsx                  # небольшое изменение регистрации/навигации
services/                     # отдельные runtime-сервисы при реальной необходимости
test/                         # текущая структура unit/integration/API/UI/evals
tools/quality/                # предлагаемые проверки собственных границ
docs/develop/                 # архитектура и сведения о расхождении с upstream
deployment/linux-pg/          # собственный профиль выпуска
docker/                       # upstream-составляющие без массовой перестройки
```

В дереве существующие пути показаны вместе с проектируемыми `domain`, `application`, `adapters`; эти слои пока не выделены. Малому модулю достаточно файлов вместо пакетов. При выделении потребители переводятся сразу, старые внутренние прокси не сохраняются.

В Python импорт подмодуля запускает родительский `__init__.py`. Сейчас `api/apps/__init__.py` создаёт приложение. Поэтому размещение чистого кода внутри `api/apps/business_documents` само по себе не обеспечивает импорт без bootstrap. Сначала это проверяется изолированным тестом. Если родитель запускает I/O, чистую собственную часть целиком вынести в отдельный пакет `business_documents/` на верхнем уровне, оставив в `api/apps` только транспорт. Такое точечное выделение с обновлением package metadata предпочтительнее переписывания всего bootstrap ядра; вторую копию бизнес-логики не оставлять.

Стандартные Peewee/GORM-модели остаются на upstream-путях. Собственные модели по возможности находятся в своём модуле; если механизм ядра требует центральной регистрации, сохраняется минимальная точка подключения. Уже работающие таблицы не переименовываются только ради нового namespace. Новые собственные таблицы получают явную принадлежность модулю и отдельную историю миграций.

В Go собственная новая возможность получает небольшой предметный пакет в `internal`, только если действительно исполняется в Go. Использовать существующий runtime, storage и parser; не копировать их внутрь расширения. Не создавать второй language-port без требования продукта.

Во frontend собственные страницы используют штатные компоненты, темы и HTTP transport. В общих routes/navigation остаются подключения; логика бизнес-документов не добавляется в общий layout. Глобальные state/providers не дублируются. Не менять структуру всех страниц или библиотеку UI для изоляции одной функции.

## 5. Правила зависимостей

Следующие запреты действуют для собственных слоёв и новых локальных интеграций. Они не являются обязательным рефакторингом всей кодовой базы upstream.

| Область | Может зависеть от | Запрещено |
| --- | --- | --- |
| Domain | stdlib, собственные типы, чистые базовые типы | Quart/Gin, ORM, Redis, HTTP clients, переменные окружения, глобальные клиенты |
| Application | domain, порты, публичные контракты разрешённых модулей | Конкретные DAO/SDK, HTTP request/session, создание соединений |
| Adapters | порты application, domain, библиотека интеграции | Управление HTTP-ответом из DB/LLM-адаптера |
| Transport | application, DTO, middleware аутентификации | SQL, DAO, поисковый клиент, самостоятельное выполнение бизнес-транзакции |
| Bootstrap | Конкретные адаптеры, сценарии и transport | Бизнес-правила |
| Чистые parser/canvas алгоритмы | Собственные типы, узкие порты, библиотеки алгоритмов | HTTP-обработчики, tenant DB services, UI |
| Собственные общие helpers | stdlib или ограниченные базовые библиотеки | Скрытые обращения к бизнес-модулям или ядру |

Направление вызова и направление импорта различаются: application вызывает repository через порт, а реализация repository импортирует определение порта. Bootstrap создаёт объекты и связывает зависимости. Внутри процесса это обычные вызовы, без обязательных HTTP-прокси и event bus.

Конкретные правила для автоматизации после выбора физического пути модуля:

- Собственный `domain` не импортирует ядро с I/O, ORM, web-framework и собственные adapters.
- Собственный `application` не импортирует конкретные adapters; импорт и тестирование чистых слоёв не запускают приложение.
- Публичный контракт модуля не реэкспортирует Peewee/GORM-модели и не запускает bootstrap.
- Собственные UI model/types не импортируют визуальные компоненты; собственный API-клиент использует штатный transport.
- Собственный Go handler обращается к сценариям; запрет прямого DAO-доступа не распространяется автоматически на неизменённые upstream-handlers.
- Ядро может импортировать собственный модуль только в перечисленных точках подключения: route, registry, model registration, worker entrypoint. Другие новые обратные зависимости блокируются.
- Интеграционный адаптер получает разрешение только на нужные сервисы/символы ядра. Возврат ядром ORM-объекта преобразуется в собственный DTO до передачи в application.

Проверяются прямые и транзитивные обходы границ собственных слоёв, а также новые циклы. Разрешённый вход адаптера в ядро — явная граница графа: старые внутренние связи ядра не превращаются в долг расширения. Динамические импорты покрываются загрузкой реестров. Адаптер — перевод контракта на реальной границе зависимости, без параллельных реализаций для множества старых версий. Поддерживаемая upstream-база у выпуска одна.

## 6. Процессы, данные и жизненный цикл операций

Этот раздел задаёт правила собственных операций. Стандартные механизмы RAGFlow используются как есть через адаптер; менять их семантику следует только ради конкретного требования или исправления с тестом.

Web/SDK/MCP → API/CLI adapter → application → domain; application обращается к DB, object storage, поиску и моделям через адаптеры. Воркер входит в тот же application через задание. Сетевое разделение нужно только там, где действительно есть отдельный процесс или внешний сервис.

### 6.1 Источники истины

- Транзакционная БД выбранного профиля: пользователи, права, метаданные, ревизии, задания и статусы. PostgreSQL/MySQL не становятся двумя одновременно записываемыми master-хранилищами.
- Object storage: исходные файлы и бинарные результаты. В БД — ссылка, владелец, checksum, размер и состояние публикации.
- Поисковый движок: восстанавливаемая проекция. Индекс не является источником прав и окончательного состояния документа.
- Redis: очередь, краткоживущие блокировки, cache и допускающие потерю данные. Если checkpoint нужен для гарантированного восстановления, его durability должна быть обеспечена явно: постоянным хранилищем либо документированной конфигурацией Redis и проверкой восстановления.
- LLM-выход: недоверенный результат вычисления. До записи валидируются структура, ссылки на evidence и разрешённое изменение состояния. Модель не решает вопросы авторизации.

### 6.2 Долгие операции

1. API валидирует вход и передаёт проверенный actor/tenant в сценарий.
2. Сценарий проверяет права и предусловия, в одной DB-транзакции создаёт операцию и запись задания. Если существующая DB job-таблица уже обеспечивает доставку, используется она; отдельный outbox нужен для надёжной публикации во внешний broker.
3. Dispatcher/worker получает идентификатор задания. Повторная доставка ожидаема: уникальный ключ операции, номер попытки и атомарный захват предотвращают повторное применение результата.
4. Внешние вызовы и LLM выполняются вне длительной DB-транзакции. Повторы разрешены для классифицированных временных ошибок с ограничением числа попыток, времени и jitter.
5. Перед фиксацией результата повторно проверяются версия агрегата, отмена и необходимые актуальные права. Устаревший worker не может перезаписать результат новой попытки; используются version/fencing token.
6. Результат и статус фиксируются атомарно в пределах БД. Между БД, object storage и индексом используются промежуточные состояния, повторяемые действия и reconciliation, а не предположение об общей транзакции.
7. API отдаёт operation ID; клиент читает статус или поток событий. Потеря SSE-соединения не превращает завершённую операцию в новую.

Состояния задания: queued → running → succeeded / failed / cancelled. Ожидание пользователя и retry описываются отдельно, когда нужны сценарию. Допустимые переходы задаются кодом владельца и проверяются тестами. Терминальный статус не меняется без явно определённой новой операции.

Ошибки классифицируются как validation, forbidden, not_found, conflict, dependency_unavailable, internal. Application не знает HTTP-кодов; transport сохраняет действующие внешние envelopes, пока они являются поддерживаемым контрактом. Добавлять вторую внутреннюю реализацию ради старого имени запрещено.

### 6.3 Эксплуатационные границы

- Actor, tenant, request ID, operation ID и deadline передаются явно; секреты и полное содержимое документов в общий лог не попадают.
- Логи/трейсы связывают API, очередь, worker и вызов модели. Метрики измеряют возраст очереди, число повторов, ошибки зависимостей, длительность этапов и задержку индекса.
- Размер файла, число параллельных задач и потребление памяти ограничиваются у владельца ресурса. Нельзя маскировать блокирующий I/O в async-функции; sync/native работа получает ограниченный executor или отдельный процесс.
- Shutdown прекращает приём, завершает либо освобождает захваченные задачи, закрывает соединения. Readiness и liveness проверяют разные состояния.
- Миграции выполняет один release-runner; Python и Go не запускают конкурирующее изменение одной схемы. Возможность отката данных задаётся миграцией отдельно от отката бинарного образа.

### 6.4 Собственные данные при обновлении ядра

Стандартные пользователь, tenant, dataset и file остаются во владении RAGFlow. Расширение хранит их идентификаторы и свои данные: ревизии, решения, задания и evidence. Перед чтением или действием адаптер вызывает актуальные проверки доступа ядра; собственная роль не даёт обходить доступ к dataset.

Для каждой связи с upstream-таблицей зафиксировать тип идентификатора, поведение удаления и нужные ограничения. Не копировать upstream-таблицы в собственную схему и не читать секреты в обход штатного сервиса. Изменение общей таблицы, если оно действительно необходимо, становится учтённым изменением ядра с отдельным тестом миграции.

История собственных миграций отделена от стандартной: уникальные идентификаторы и учёт выполненных шагов. Для каждого обновления release manifest задаёт точный порядок upstream- и собственных миграций с учётом зависимостей. Старые worker/API должны быть остановлены перед несовместимым изменением схемы. Bootstrap новой upstream-версии не должен удалять или пересоздавать собственные таблицы; это проверяется на восстановленной копии данных.

## 7. Подходы к написанию кода

Правила применяются к собственному коду и затронутым локальным участкам. Форматирование или переименование соседнего стандартного кода не включается в изменение без необходимости: такой diff повышает стоимость следующего merge.

**Сначала сценарий и инвариант.** Изменение начинается с поиска владельца поведения и потребителей. Если возможность уже существует, использовать её. Новая абстракция должна решать текущую зависимость, вариативность или границу I/O; абстракции «на будущее» не добавляются.

**Одна причина изменения.** Функция выполняет один понятный шаг. Если в одном методе смешаны доступ, SQL, prompt, retry и HTTP-ответ, разделение проводится по обязанностям. Количество строк — сигнал ревью, а не самостоятельный критерий качества.

**Явные данные.** На границах применяются типизированные DTO/команды и валидация. Внутри domain не передаются универсальные dict/map с неявными ключами. Для внешних payload допустим `unknown`/сырой JSON до проверки, после неё — конкретный тип.

**Минимальная публичная поверхность.** Helper остаётся приватным, пока не появился реальный внешний потребитель. Интерфейс определяется нуждами вызывающей стороны. Не создавать `BaseService`, универсальный CRUD repository, manager/factory для каждого класса или DI-контейнер без практической необходимости.

**Повторение оценивается по смыслу.** Две одинаковые строки не требуют общего helper. Дублирование правила доступа, перехода состояния, расчёта версии или обработки retry требует одного владельца. Не объединять разные предметные понятия только из-за похожей структуры.

**Язык и ошибки.** Имена отражают предметную область; комментарии объясняют причину или инвариант. История переноса остаётся в Git. Нельзя глотать исключения, выдавать успешный результат после ошибки зависимости или заменять обязательную интеграцию пустой заглушкой.

| Контур | Конкретные правила |
| --- | --- |
| Python | Аннотации публичных границ; небольшие Protocol для I/O; чистые domain-функции; контекстные менеджеры транзакций; конфигурация и клиенты создаются при старте, не при импорте |
| Go | Короткие предметные пакеты; интерфейсы у потребителя; `context.Context` для отменяемой работы; обработка и оборачивание ошибок с сохранением причины; контролируемый lifecycle goroutine |
| TypeScript/React | Strict уже включён; сохранять его; `unknown` с проверкой вместо `any`; запросы и состояние функции рядом; бизнес-правила не прятать в JSX; derived state не дублировать в нескольких store |
| SQL и хранение | Tenant-scoped запросы; уникальные ограничения для инвариантов; проверка конфликтов версий; отсутствие внешних вызовов внутри длинной транзакции |
| Prompt/DSL/assets | Версия схемы и проверка структуры; тест на загрузку; один канонический asset; golden/eval проверяет поведение, а не только наличие текста |

## 8. Контроль мёртвого и лишнего кода

Практический алгоритм обнаружения, режимы автоматического удаления и протокол упрощения сложных алгоритмов — в [непрерывной очистке кода](continuous-code-simplification-ru.md). При разработке цикл выполняется после законченного изменения и перед завершением задачи; новые инструменты применяются после их внедрения и проверки.

Полный отчёт анализатора может охватывать весь репозиторий, но обязательное устранение находок разграничивается по происхождению. Собственный подтверждённый мёртвый код удаляется. Стандартный код не удаляется только из-за отсутствия использования в текущем локальном профиле. Настоящий дефект или лишний код upstream сначала проверяется по поддерживаемым им профилям; необходимое локальное исправление учитывается как изменение ядра.

Разделять четыре категории:

| Категория | Признак | Решение |
| --- | --- | --- |
| Мёртвый код | Недостижим от поддерживаемых точек входа | Удалить после проверки динамики и контрактов |
| Дублирующая реализация | Два пути выражают одно актуальное правило | Выбрать владельца, перенести потребителей, удалить второй путь |
| Лишняя абстракция | Нет полезной границы, вариативности или самостоятельного смысла | Встроить в владельца, сократить интерфейс |
| Устаревший продуктовый путь | Код достижим, но возможность больше не поддерживается | Сначала подтвердить решение о поддержке; затем удалить маршрут, UI, конфигурацию и тесты вместе |

Код с нулевым coverage не обязательно мёртвый. Вызов только из теста не доказывает нужность runtime-кода. Отсутствие вызовов в коротком наблюдении также не доказывает отсутствие потребителя. Старые миграции могут быть обязательны для поддерживаемого обновления.

### 8.1 Источники достижимости

При проверке учитываются HTTP/SDK/MCP routes, CLI commands, worker task types, расписания, registry/entrypoints, строки DSL, сохранённые canvas, конфигурация сборки и запуска, Vite lazy imports, Storybook, assets, а также нативные build tags и bindings.

Реестр загрузки должен быть единственным источником регистрации. Анализатор получает из него entrypoints либо проверяет согласованность своей конфигурации с реестром. Нельзя поддерживать отдельный ручной список «всего используемого» без проверки существования символов.

Для persisted DSL перед удалением компонента нужна инвентаризация используемых типов и преобразование сохранённых данных, если тип больше не поддерживается. Имя `old`, `legacy`, `next` или `deprecated` — повод проверить назначение, но не разрешение удалить рабочую функцию по имени.

### 8.2 Набор проверок

Инструменты ниже — предлагаемые дополнения. Их версии нужно закрепить в зависимостях при внедрении; запуск через автоматически скачиваемый `latest` в обязательном CI не допускается.

| Область | Средство | Ограничение |
| --- | --- | --- |
| Python unused imports/locals | Существующий Ruff | Не доказывает достижимость функций и runtime-регистраций |
| Python unused symbols | [Vulture](https://github.com/jendrikseipp/vulture) | Confidence — свойство анализа, не доказательство отсутствия внешнего контракта; whitelist только по проверенным ложным срабатываниям |
| Python import boundaries | [Import Linter](https://import-linter.readthedocs.io/en/latest/contract_types/forbidden/) | Проверяет ограничения импортов, включая косвенные; динамические пути требуют отдельных тестов |
| Frontend unused files/exports/dependencies | [Knip](https://knip.dev/overview/getting-started) | Нужна конфигурация entrypoints, assets и инструментальных файлов |
| Frontend dynamic imports | [Конфигурация и разбор результатов Knip](https://knip.dev/guides/handling-issues) | Шаблонные пути и нераспознанные конфигурации дают ложные срабатывания |
| Go correctness/unused | [Staticcheck, U1000](https://staticcheck.dev/docs/checks/#U1000) | Не заменяет проверку внешних контрактов, build profiles и нативных связей |
| Межмодульные зависимости TS/Go | ESLint-ограничения импортов; небольшой Go import checker | Проверять разрешённые ребра, а не совпадения текста в комментариях |
| Дублирование и избыточность | Предметное ревью, при необходимости отчёт клонированных блоков | Автоматическая метрика не определяет одинаковый бизнес-смысл |

### 8.3 Цикл удаления

1. Получить кандидатов статическим анализом и поиском потребителей, включая динамические входы.
2. Для каждого кандидата записать символ/путь, причину, доказательство использования либо отсутствия, владельца и действие. Подтверждённую находку по возможности удалить сразу, без отдельного бюрократического реестра.
3. Проверить внешний контракт, сохранённые данные, поддерживаемые профили и deploy scripts.
4. В одном изменении удалить собственную реализацию, регистрацию, импорт, настройку, ненужную собственную зависимость, obsolete-тест и документацию. Общую upstream-зависимость не удалять по результатам анализа только расширения. Сохранить тесты актуального поведения на единственном оставшемся пути.
5. Выполнить сборку, тесты потребителей и проверку загрузки реестра. Для удаления обработчика сверить route/command inventory с ожидаемым набором.
6. Повторить анализ: удаление одной функции может сделать мёртвой следующую.

Автоматическое массовое удаление по отчёту анализатора не применяется. Generated/vendor/native assets учитываются отдельными правилами, а не удаляются как обычный прикладной код. Возврат удалённой реализации при необходимости делается через Git, не через закомментированный блок.

При каждом обновлении проверять собственные исправления ядра: если upstream уже решает ту же задачу, подтвердить эквивалентность поведения тестами и убрать локальное исправление и запись о нём. Функциональность не сохраняется в двух реализациях. Совпадение названия функции или текста commit не является доказательством эквивалентности.

## 9. Автоматическое соблюдение архитектуры

### 9.1 Обязательные проверки

Два независимых результата: здоровье стандартной сборки/тестов и качество собственных модулей/границ. Успех одного не заменяет другой. Новые обязательные architecture gates охватывают собственный код и учтённые изменения ядра; upstream-imports не переписываются ради прохождения локального правила.

Существующие Lefthook и regression lanes сохраняют свою роль. Новые проверки должны запускаться независимо от PR label: текущий `tests.yml` использует условие с меткой `ci`, поэтому одного добавления шага в этот job недостаточно для обязательного контроля каждого PR. Нужен отдельный всегда запускаемый required job или изменение условий с учётом runner budget.

| Уровень | Проверки | Условие отказа |
| --- | --- | --- |
| Локально | Форматирование, lint изменённых файлов, точечные тесты | Ошибка инструмента или теста |
| Каждый PR, быстрый required job | Границы расширений, учёт изменений ядра, lint/typecheck, lock consistency, исключения, unit/contracts | Новое собственное нарушение, неучтённое изменение ядра, просроченное исключение, незапущенная проверка |
| PR с изменением wiring/DSL/registry | Загрузка всех включённых компонентов, route inventory, тесты сериализации | Потерянная регистрация, неизвестный тип, неверный контракт |
| PR с изменением БД/очереди | Реальная БД: конфликт версии, повторная доставка, cancel/retry, миграция | Нарушение инварианта или отсутствие обязательного окружения |
| PR с изменением runtime/native | Сборка нужного профиля, Go package tests, адаптерные интеграционные тесты | Build/profile failure |
| Полный периодический прогон и релиз | Весь граф с разделением по происхождению, dead-code inventory, regression lanes, поддерживаемые профили, качество retrieval/LLM | Регресс или неразобранные обязательные нарушения |
| Интеграция upstream-релиза | Контракты адаптеров, собственные функции и данные, штатные сценарии, upgrade с предыдущего выпуска, восстановление | Потеря функции/данных/прав, конфликт схемы или неподтверждённое восстановление |

Это проект периодического CI, а не созданная автоматизация. Полный прогон ловит влияние вне diff. Изменение общей конфигурации, lockfile, генератора или корневого контракта расширяет область проверки. Отсутствие зависимостей не должно превращаться в «успех со skip» для обязательного контура.

### 9.2 Введение правил в существующее дерево

Для каждого нового правила сначала получить проверенный baseline. Запись содержит rule ID, источник и целевую зависимость/символ, владельца, причину и срок устранения. Идентификатор не привязывать только к номеру строки.

Baseline здесь содержит долг собственного кода и локальных изменений ядра. Наблюдаемые особенности неизменённого upstream хранятся отдельно без искусственных сроков на его переписывание. Появившиеся в новом upstream зависимости сверяются с выбранным commit; они не разрешают добавлять такое же нарушение в собственный код. Регрессы поведения при этом остаются блокирующими независимо от происхождения.

- Новые нарушения блокируют PR сразу после настройки достоверного анализа.
- Старые нарушения не растут; PR, меняющий соответствующую границу, устраняет относящееся к нему нарушение.
- Базу нельзя автоматически пересоздавать поверх новых проблем. CI сравнивает с базовой веткой; изменение baseline требует ревью владельца модуля.
- Исправленное нарушение исчезает из baseline; оставшаяся запись о несуществующем нарушении считается ошибкой.
- Временное архитектурное исключение имеет issue, владельца и конечную дату. После срока CI падает.
- Постоянная динамическая точка входа — часть регистрации с тестом загрузки, а не бессрочное исключение «не анализировать этот каталог».

### 9.3 Небольшой набор файлов для реализации контроля

Создавать недостающие файлы на соответствующем этапе внедрения; наличие T0-реестра или частичного T2-runner не означает готовность всего набора:

| Файл | Назначение |
| --- | --- |
| `tools/quality/module-map.yaml` | Владельцы модулей, пути и разрешённые межмодульные ребра; проверка существования всех путей |
| `tools/quality/baseline.json` | Только разобранные старые нарушения и временные исключения |
| `tools/quality/upstream-base.json` | Полный upstream commit/tag последней принятой базы, проверяемый URL источника; это не текущий HEAD форка |
| `tools/quality/core-changes.yaml` | Собственные изменения стандартных файлов: путь, причина, владелец, integration contract/test, статус относительно upstream |
| Конфигурации в `pyproject.toml`, `web/knip.json`, ESLint | Нативные настройки анализаторов, без дублирования их функциональности собственными сканерами |
| `tools/quality/check_architecture.py` | Тонкий запуск/сбор отчётов и сверка baseline; не новый универсальный framework анализа кода |
| `.github/CODEOWNERS` | Реальные ответственные за модули, контракты, миграции и quality config |
| `.github/workflows/architecture.yml` | Required job и сохранение отчёта; имя job стабильно для branch protection |
| `docs/develop/adr/` | Короткие решения о существенных границах, владении и внешних контрактах |

Отчёт CI: commit, версия инструмента, профиль, область сканирования, результат, новые/устранённые нарушения и список исключений. Если область не проанализирована, отчёт явно показывает это. Установка required checks в защите ветки — отдельное действие при внедрении; локальный YAML сам по себе запрет merge не обеспечивает.

Проверка изменений ядра сравнивает дерево кандидата с явно записанным upstream commit, затем сверяет оставшийся fork-diff с реестром. Имя remote-ветки и один `merge-base` не заменяют закреплённую принятую базу. Новые upstream-файлы, совпадающие с выбранной версией, не считаются собственной доработкой. Реестр классифицирует diff и не хранит дубликаты патчей: история реализации остаётся в Git.

## 10. Тесты и критерий завершения изменения

Тестируется поведение владельца, а не совпадение текста реализации. Unit-тесты domain не запускают Quart, Redis, MinIO или модель. Application тестируется с небольшими fake-адаптерами. Интеграционные тесты проверяют реальные ограничения БД/хранилища. Контрактные тесты фиксируют HTTP/SDK/DSL и различия поддерживаемых runtime-профилей.

LLM/retrieval требуют двух видов проверки: детерминированные тесты состояния/структуры и eval на фиксированных примерах качества. Запись версии модели, prompt и dataset обязательна для сравнимости результата. Сетевой live smoke не заменяет детерминированные проверки, а mocked UI не доказывает работу backend.

Не назначать произвольные 100% coverage всему проекту. Существующие пороги не снижать. Для выделяемого модуля измерить исходное покрытие, защитить критические переходы, ошибки и ветви, затем закрепить достигнутый минимум. Уменьшение scope измерения ради прохождения gate запрещено. Новое критическое правило должно иметь негативный сценарий, даже если общий процент уже достаточен.

Перед завершением изменения:

- У сценария один владелец, у записи — одна транзакционная граница.
- Зависимости разрешены, публичная поверхность минимальна.
- Входные данные, actor/tenant, конфликт версии и ошибки обработаны на своих границах.
- Старый путь, его регистрации и лишние зависимости удалены; поддерживаемые данные и внешние контракты учтены.
- Проверены затронутые потребители и необходимые build profiles.
- Документация соответствует текущему пути, а новый обязательный check действительно запускается и способен упасть.
- Для изменения ядра указаны причина и проверка поведения на закреплённой upstream-базе; расширение не зависит от ядра вне своих адаптеров.

Точечные проверки опираются на текущие команды: Python — `uv run pytest <путь>` и Ruff; frontend — scripts `lint`, `type-check`, `test`, `build`; Go — `bash build.sh --test ./internal/<package>/...`. Go native проверки выполняются в окружении `build.sh`, а не заменяются сырыми `go test`/`go build` на Windows. Подключение Staticcheck должно использовать те же build tags, CGO flags и нативные зависимости.

## 11. Порядок внедрения

Каноническая последовательность и критерии приёмки — в [плане перехода T0–T7](architecture-transition-ru.md). Сначала фиксируются база и собственный diff, затем защищается текущее поведение, проверяется точность анализаторов и включается контроль новых нарушений. После этого выполняются пилот business_documents, изоляция остальных интеграций, согласование сборки и пробное upstream-обновление. Последний этап переводит проверки в обычный процесс сопровождения.

Этапы — последовательность проверяемых изменений, не календарная оценка. Любое точечное выделение собственного модуля включает потребителей, тесты, упаковку и удаление освобождённого пути. Второй внутренний API и копия ядра внутри расширения не создаются. Поддерживаемые внешние контракты и persisted DSL проверяются до удаления их обработчиков.

Массовое переименование стандартных каталогов, переписывание task_executor/canvas и выбор единственного языка для всего RAGFlow в план не входят. Выбор менеджера зависимостей следует поддерживаемому install-потоку принятого upstream-релиза, а не предпочтению отдельного нового workflow.

## 12. Метрики поддержания чистоты

| Метрика | Целевое правило |
| --- | --- |
| Новые запрещённые зависимости собственных модулей | 0 после включения соответствующего gate |
| Новые циклы собственных модулей | 0 |
| Рост разобранного baseline | 0 без отдельного обоснованного решения |
| Просроченные исключения | 0 |
| Обязательные проверки, которые были пропущены | 0 |
| Динамические входы без проверки загрузки | Сокращение до 0 по поддерживаемым профилям |
| Подтверждённый мёртвый код | Удаляется в текущем изменении либо получает владельца и срок |
| Публичные symbols, зависимости, крупные модули | Отслеживать изменение и причины; не вводить бессмысленную квоту строк |
| Неучтённые собственные изменения ядра | 0 |
| Размер core-diff и число точек подключения | Измерять относительно закреплённой upstream-базы; рост обосновывать, не оптимизировать число строк за счёт читаемости |
| Время обновления и ручные конфликты | Записывать по каждому upstream-релизу; повторяющиеся места направлять на изоляцию |
| Потерянные собственные функции или данные после обновления | 0 по согласованному набору проверок |

Чистота поддерживается сочетанием владельцев, исполняемых ограничений и удаления ненужного. Документ считается внедрённым только после появления соответствующих проверок и подтверждённого изменения реальных путей выполнения.

## 13. Процедура обновления из upstream

### 13.1 Ветки и версии

`origin/main` содержит собственную интегрированную историю. `upstream` служит источником обновлений. Кандидат готовится в отдельной ветке `codex/upstream-<release>` и отдельном worktree от зафиксированного состояния собственного выпуска. Использовать merge выбранного upstream commit; не переписывать опубликованную историю форка rebase или force push. Не подменять собственную main содержимым upstream.

Каждый выпуск записывает собственный commit/tag, полный принятый upstream commit/tag, версии образов/зависимостей и собственных миграций. Собственная версия не считается номером upstream-релиза. Предпочитать конкретный проверяемый release commit плавающему `upstream/main`.

### 13.2 Подготовка

1. Зафиксировать нужные собственные изменения в проверенном commit. Проверить также untracked файлы. Отдельный worktree не содержит незакоммиченные наработки автоматически; не принимать результат проверки такого неполного кандидата за проверку всей текущей версии.
2. Получить свежие upstream refs, выбрать целевой релиз, прочитать его release notes и требования к runtime, схеме, DSL и индексам. Не считать локальный remote ref свежим без fetch.
3. Составить список затронутых интеграционных контрактов и собственных изменений ядра. Проверить, какие локальные исправления уже включены upstream.
4. Подготовить изолированное окружение и согласованную копию БД, object storage и необходимых конфигураций/секретов. Данные для тестирования ограничить требуемым набором. Индексы восстанавливаются, если это доказано для данного профиля; невосстанавливаемые checkpoints требуют отдельной копии.
5. Зафиксировать точку восстановления и проверить процедуру восстановления. Копия одного Git-дерева не является резервной копией бизнес-данных.

### 13.3 Слияние и проверка кандидата

1. Влить выбранный upstream commit в integration-ветку. Конфликты разбирать по смыслу, с учётом обеих сторон. Нельзя применять массовый выбор ours/theirs, исключать целые свои каталоги из merge или копировать их поверх новой версии без проверки контрактов.
2. Адаптировать только затронутые интеграции и необходимые изменения ядра. Если контракт upstream изменился, обновить адаптер и его тест; не разветвлять реализацию на все исторические версии.
3. Обновить запись принятой upstream-базы и реестр core-diff в кандидате. Удалить действительно заменённые upstream локальные исправления после проверки эквивалентности.
4. Собрать кандидата с закреплёнными зависимостями и новым требуемым окружением. Выполнить применимые штатные тесты ядра, проверки собственных границ и все контрактные тесты адаптеров.
5. На копии предыдущей собственной поставки выполнить миграции в записанном порядке. Проверить старые документы, ревизии, evidence, роли, ссылки на datasets/files, сохранённые canvas и незавершённые задания. Новая пустая БД не заменяет тест обновления.
6. Выполнить полные применимые regression lanes из `test/REGRESSION.md`: unit, API, UI, реальные зависимости, native-профили и evals. Для собственных возможностей проверить создание/изменение документа, права, поиск, экспорт, EVA/ASR и другие функции из инвентаризации.
7. Проверить стандартные сценарии RAGFlow: вход, dataset upload/parse, retrieval/chat, agent run. Отсутствие merge-конфликтов или успешный compile не доказывает сохранение поведения.
8. Сохранить отчёт: target commit, разрешённые конфликты, изменённые адаптеры, результаты тестов, данные до/после миграций и результат восстановления. Обязательная проверка без окружения означает непроверенный кандидат, не готовность к выпуску.

### 13.4 Выпуск и восстановление

После успешной проверки кандидат включается в собственную main обычным проверяемым потоком и получает собственный release tag. Рабочая поставка обновляется отдельной операцией деплоя. Изменения main за время подготовки повторно интегрируются в кандидат и проверяются до выпуска.

Для несовместимой миграции запланировать остановку записи и worker, сделать актуальную согласованную копию, выполнить миграции и старт новой версии. Старые и новые несовместимые writer не должны одновременно работать с одной БД. После запуска повторить критический smoke и сверку собственных данных.

Откат образа допустим только при подтверждённой работе старой версии с новой схемой. Иначе нужен план исправления вперёд либо согласованное восстановление БД/объектов/конфигурации. Восстановление старой копии теряет записи после её создания; допустимое окно потери и остановки записи определяется до выпуска. Нельзя обещать откат только командой Git.

Ожидаемый результат: собственные функции и данные сохраняются, а изменения при обновлении сосредоточены в ограниченном наборе интеграций. Гарантировать, что собственные файлы никогда не потребуют изменения, эта схема не может.
