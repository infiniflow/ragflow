# Структура руководства пользователя раздела «Документы»

Статус: границы зафиксированы по результатам ревью. Дата: 2026-09-06.

Документ задаёт структуру будущего русскоязычного руководства по работе с
документами бизнес-требований и доступным обычному пользователю операциям
учётной записи в текущей локальной поставке RAGFlow. Это не готовое руководство
и не подтверждение, что каждый сценарий уже проверен в работающей среде.

## 1. Объём и обязательные границы

Руководство охватывает только:

1. Раздел **Документы**:
   - создание документа бизнес-требований;
   - продолжение сохранённой работы;
   - сбор и анализ вводных;
   - создание черновика и внесение изменений;
   - вопросы, комментарии и предложения;
   - применение подтверждённых изменений;
   - ревизии, экспорт и архив;
   - связь с EVA, подготовку и публикацию изменений;
   - действия, доступные разным ролям.
2. Доступные обычному пользователю операции учётной записи:
   - экран **Профиль**: поля **Имя**, **Аватар**, **Часовой пояс**, **Email**
     только для чтения, **Пароль** и **EVA API токен**;
   - отдельный экран **Провайдеры моделей**: только поле **LLM**;
   - переключение темы и выход из системы в оболочке настроек.

Первая версия руководства относится к русскому веб-интерфейсу в настольном
браузере. Мобильная компоновка, API, CLI и административный интерфейс не входят
в объём до отдельной проверки и решения о расширении границ.

Фраза «доступные опции профиля» в рамках этого документа означает перечисленный
контур учётной записи. Она не означает все разделы **Настроек** и не объединяет
экран **Профиль**, экран выбора модели и общие действия оболочки в одну форму.

В руководство не входят базы знаний, файлы, поиск, чат, агенты, память,
OpenMetadata, источники данных, каналы чата, MCP, команда, API, установка,
эксплуатация и административная панель.

Администраторские действия упоминаются только в двух случаях:

- чтобы объяснить, почему пользователю недоступна кнопка или операция;
- чтобы точно сформулировать, с каким запросом обратиться к администратору.

### 1.1 Контракт включения

| Область | В руководстве | Граница описания |
| --- | --- | --- |
| Раздел **Документы** | Да | От открытия списка до проверяемого результата пользовательского действия |
| Ролевые действия с документом | Да | Только действия, реально разрешённые текущей ролью, владением, состоянием и `allowed_commands` |
| Пользовательские операции EVA из **Документов** | Да | Привязка, чтение, подготовка, проверка и подтверждаемая публикация |
| Экран **Профиль** | Да | Только видимые поля и персональный EVA-токен |
| Экран **Провайдеры моделей** | Частично | Только выбор LLM (чат-модели) из уже доступного списка и его влияние на **Документы** |
| Тема и выход | Да | Только переключение темы и завершение своей сессии |
| Получение персонального токена в EVA | Частично | Краткая обязательная предпосылка; не руководство по EVA |
| Настройка EVA-коннектора | Нет | Адрес, пространство, сервисный токен, SSL и фоновая синхронизация относятся к администрированию |
| Управление моделями | Нет | Провайдеры, ключи, URL, добавление моделей и модели других типов не описываются |
| Управление ролями и доступом | Нет | В руководстве показываются последствия назначенной роли, но не её выдача |
| Остальные возможности RAGFlow | Нет | Не становятся отдельными главами, даже если используются системой как зависимость |

Зависимость не расширяет границу руководства. Например, использование базы
знаний при анализе требований не добавляет главу по базам знаний, а отсутствие
сервисного EVA-токена не добавляет инструкцию по администрированию коннектора.

### 1.2 Правило изменения границ

Новая страница включается только тогда, когда одновременно выполняются условия:

1. сценарий начинается в **Документах**, на одном из разрешённых экранов учётной
   записи либо в доступном элементе оболочки настроек;
2. пользователь может самостоятельно выполнить хотя бы одно описываемое
   действие;
3. страница заканчивается проверяемым пользовательским результатом;
4. тема не требует администраторской настройки продукта или другой подсистемы.

Исключения и новые продуктовые разделы добавляются только отдельным решением по
ревью этой структуры. Ссылку на внешнюю или администраторскую инструкцию можно
дать как предпосылку, не копируя её содержание.

## 2. Термины

### 2.1 Канонический словарь

| Термин руководства | Значение и правило употребления |
| --- | --- |
| **Документы** | Точное название раздела в глобальном меню. |
| Документ бизнес-требований | Основной объект работы. На каждой странице использовать полную форму при первом упоминании, далее допустимо «документ». Не использовать «деловой документ» и «бизнес-документ». |
| Бизнес-требования | Содержание документа или заголовок формы создания, но не название самостоятельного типа файла. |
| Черновик | Результат действия **Создать черновик** до согласования. После фиксации версии использовать отображаемое понятие «ревизия». |
| Ревизия | Зафиксированная версия содержания документа; в интерфейсе отображается как **Ревизия N**. |
| Внесение изменений | Этап уточнения документа с вопросами, комментариями и предложениями. |
| Обсуждение | Точная подпись панели с вопросами, ответами, предложениями и комментариями текущего цикла внесения изменений. В пользовательском тексте не использовать внутреннее название «протокол». |
| Владелец | Пользователь, которому назначен документ и который может его редактировать в рамках роли и состояния. |
| Страница EVA | Внешняя страница, с которой связывается документ бизнес-требований. В повествовании предпочитать эту форму; «документ EVA» использовать только в точной подписи интерфейса. |
| Привязка к EVA | Связь документа со страницей EVA. Привязка сама по себе не изменяет страницу. |
| Публикация в EVA | Отдельное подтверждаемое действие, изменяющее видимую страницу EVA. |
| Персональный EVA-токен | Пользовательские учётные данные для доступных операций EVA. Точную подпись поля **EVA API токен** цитировать без редакционного исправления. |
| LLM (чат-модель) | В первом объяснении использовать обе формы. **LLM** — точная подпись поля, «чат-модель» — поясняющий термин руководства. |

Названия **Рабочие документы** и **Сохранённые документы** не являются
синонимами объекта:

- **Рабочие документы** — точный заголовок страницы;
- **Сохранённые документы** — точный заголовок области со списком.

В готовом руководстве полужирным выделяются точные названия меню, полей, кнопок,
диалогов и видимых состояний. Поясняющие термины пишутся обычным начертанием,
кроме места их определения.

### 2.2 Состояния документа и операции

В пользовательском тексте используются только русские подписи интерфейса:

| Вид | Точные подписи |
| --- | --- |
| Состояние документа | **Сбор вводных**, **Внесение изменений**, **Правки внесены**, **В архиве** |
| Текущая операция | **Готово к работе**, **Анализ вводных**, **Анализ замечаний**, **Создание черновика**, **Применение изменений**, **Подготовка файла**, **Операция завершилась с ошибкой** |

Нужно различать действие, процесс и итоговое состояние:

| Смысл | Точная подпись интерфейса | Формулировка в повествовании |
| --- | --- | --- |
| Возобновить изменение согласованного документа | **Начать вносить изменения** | Начать новый цикл внесения изменений |
| Проанализировать обратную связь | **Проанализировать замечания** | Запустить анализ замечаний |
| Применить подтверждённые изменения | **Применить исправления** | Применить изменения и дождаться новой ревизии |
| Архивировать | **В архив** | Перевести документ в архив |
| Состояние после архивации | **В архиве** | Документ доступен только для чтения |
| Создать экспорт | **Создать Markdown**, **Создать HTML для EvaWiki** | Подготовить и скачать доступный файл |

`EvaWiki` сохраняется внутри точного названия **Создать HTML для EvaWiki**, а
`EVA Wiki` — внутри сообщения **В EVA Wiki найдены страницы с таким
названием**. В авторском повествовании интеграция называется EVA.

Технические идентификаторы `business_documents`, названия API-команд и значения
enum не выносятся в основной пользовательский текст. Они допустимы только в
авторской проверке и справке по ошибкам, когда код отображается пользователю.

## 3. Аудитория и права в разделе «Документы»

Руководство должно начинаться с объяснения, что состав действий зависит от роли
и владельца документа.

Проверяются две независимые оси доступа:

1. **Роль в «Документах»** определяет создание, редактирование, удаление и
   назначение владельца.
2. **Признак суперпользователя** определяет состав системных настроек. Обычный
   пользователь видит только **Профиль** и ограниченный экран
   **Провайдеры моделей** с единственным полем **LLM**; тема и выход доступны в
   оболочке настроек.

Расширенный модератор документов не становится от этого администратором
настроек. Видимость пункта **Документы**, роль, владение объектом, состояние
документа и список разрешённых сервером команд проверяются отдельно.
Для суперпользователя руководство описывает только его действия внутри
**Документов**; появляющиеся у него административные настройки остаются вне
границ.

| Роль в интерфейсе | Создавать | Редактировать | Удалять | Назначать владельца |
| --- | --- | --- | --- | --- |
| Автор-создатель | Да | Свои документы | Нет | Нет |
| Автор-редактор | Нет | Документы, где он текущий владелец | Нет | Нет |
| Модератор-создатель | Да | Все доступные документы | Нет | Нет |
| Расширенный модератор | Да | Все доступные документы | Да | Да |
| Администратор | Да | Все доступные документы | Да | Да |

Все роли могут читать доступные документы. Если действие запрещено, руководство
не предлагает искать отсутствующую кнопку: оно объясняет ограничение роли и
следующий безопасный шаг.

Видимый пункт меню не доказывает право редактирования или удаления. Если роль
разрешает редактирование, но текущие состояние и серверная команда запрещают
операцию, руководство ориентируется на фактически доступное действие.

## 4. Формат руководства

Материал строится по пользовательскому пути, а не по устройству системы:

```text
Открыть «Документы»
  ├─ Продолжить работу → Мои / Все → открыть документ
  ├─ Создать документ бизнес-требований → Новый → вводные → анализ → черновик
  ├─ Доработать страницу EVA → Доработать EVA → выбрать страницу → изменения
  ├─ Внести изменения → вопросы / комментарии / предложения → применить исправления
  ├─ Завершить работу → ревизия → экспорт / EVA → в архив
  └─ Настроить учётную запись → Профиль / LLM / тема / выход
```

Рекомендуется отдельная страница для каждого завершённого результата. Большая
одностраничная инструкция затруднит работу с ролями, ошибками и EVA-сценариями.

## 5. Предлагаемое оглавление

### 5.1 Главная страница

`index.md` — кратко отвечает на четыре вопроса:

1. Что создаётся в разделе **Документы**.
2. Как начать новый документ или продолжить существующий.
3. Почему набор кнопок зависит от роли и владельца.
4. Где открыть доступные настройки учётной записи.

На странице размещаются три входа:

- **Создать документ бизнес-требований**;
- **Продолжить внесение изменений**;
- **Настроить учётную запись**.

Это названия навигационных ссылок самого руководства, а не подписи кнопок
приложения.

### 5.2 Начало работы

1. `start/open-documents.md` — вход в систему, переход в **Документы**, состав
   рабочей области и признаки отсутствия доступа.
2. `start/choose-scenario.md` — различие между **Новый**, **Доработать EVA** и
   открытием сохранённого документа.
3. `start/quickstart.md` — короткий сквозной сценарий: создать документ, дождаться
   анализа, ответить на вопрос, получить черновик и проверить ревизию.
4. `start/roles.md` — определить доступные действия по роли и владельцу.

Быстрый старт не включает настройку администратора, базы знаний или внешних
сервисов. Если предпосылка отсутствует, даётся формулировка обращения к
администратору.

### 5.3 Список документов

1. `documents/list.md` — область **Сохранённые документы**, количество, состояния,
   владелец, время изменения, номер ревизии и текущая операция.
2. `documents/mine-and-all.md` — фильтры **Мои** и **Все**, различие пустых
   состояний и режим только для чтения.
3. `documents/open-and-resume.md` — открыть документ и определить, с какого шага
   продолжать работу.
4. `documents/list-errors.md` — повторить загрузку, понять ошибку и не создавать
   дубликат при неопределённом результате.

### 5.4 Создание документа бизнес-требований

1. `documents/create.md` — название, описание идеи, голосовой ввод и действие
   **Начать работу**.
2. `documents/title-rules.md` — уникальность названия и что делать при конфликте.
3. `documents/eva-match.md` — найденные в EVA страницы с тем же названием,
   хлебные крошки и выбор между привязкой и продолжением без привязки.
4. `documents/eva-bind-warning.md` — отдельное подтверждение: будущая публикация
   полностью заменит содержимое выбранной страницы; привязка сейчас ничего не
   публикует.
5. `documents/creation-result.md` — документ уже создан, даже если автоматический
   анализ не стартовал; как открыть его и повторить анализ без второго документа.

Руководство явно показывает случай, когда роль позволяет читать назначенные
документы, но не позволяет создавать новые.

### 5.5 Сбор вводных и черновик

1. `documents/intake.md` — состояние **Сбор вводных**, запуск анализа и ожидаемый
   результат.
2. `documents/questions.md` — карточка **Вопрос**, готовые варианты, поле **Свой
   ответ**, кнопка **Ответить** и состояния **Требует ответа**, **Ответ
   зафиксирован**, **Закрыт**. Не описывать закрытие как действие пользователя.
3. `documents/create-draft.md` — условия действия **Создать черновик**, фоновая
   операция и появление первой ревизии.
4. `documents/progress.md` — состояния **Анализ вводных**, **Анализ замечаний**,
   **Создание черновика**, **Применение изменений** и **Подготовка файла**.
5. `documents/retry-operation.md` — ошибка операции, повтор и признаки, при
   которых повторять действие не следует.

### 5.6 Внесение изменений в документ

1. `documents/start-review.md` — действие **Начать вносить изменения**, переход
   из состояния **Правки внесены** во **Внесение изменений** и доступные действия.
2. `documents/comments.md` — поле **Комментарий**, область **весь документ** или
   **выделенный фрагмент** и действие **Добавить комментарий**.
3. `documents/comment-anchor.md` — комментарий ко всему документу или
   выделенному фрагменту и сообщение **Фрагмент относится к предыдущей
   ревизии**; как проверить контекст перед применением изменения.
4. `documents/proposals.md` — карточка **Предложение**, обоснование, кнопки
   **Принять** и **Отклонить**, состояния **Ожидает решения**, **Принято** и
   **Отклонено**.
5. `documents/review-questions.md` — уточняющий вопрос, возникший после анализа
   замечаний.
6. `documents/apply-changes.md` — действие **Применить исправления**, применение
   только подтверждённых изменений и создание новой ревизии.
7. `documents/review-complete.md` — состояние **Правки внесены** и дальнейшие
   действия.

Принятое предложение не описывается как уже изменённый текст: содержание
меняется только после отдельного применения изменений и появления ревизии.

### 5.7 История и ответственность

1. `documents/revisions.md` — открыть историю, прочитать номер и дату ревизии.
2. `documents/change-basis.md` — автор изменений, инициатор, исполнитель и
   основание новой версии.
3. `documents/ownership.md` — текущий владелец и назначение нового владельца,
   доступное расширенному модератору и администратору.
4. `documents/concurrent-change.md` — конфликт версии, обновление страницы и
   повтор действия на актуальной ревизии.

### 5.8 EVA

1. `documents/eva/prerequisites.md` — наличие доступного подключения и персонального
   EVA-токена; что пользователь может проверить сам.
2. `documents/eva/start-from-page.md` — режим **Доработать EVA**, выбор страницы
   и создание управляемого изменения.
3. `documents/eva/link-status.md` — подключённая страница и сообщение
   **Только ссылка — доступный коннектор не найден**.
4. `documents/eva/pull.md` — **Перечитать текущий документ из EVA**, результат без
   изменений и новая входная версия при отличиях.
5. `documents/eva/prepare-change.md` — подготовить изменение EVA из согласованной
   ревизии.
6. `documents/eva/review-change.md` — проверить черновик и убедиться, какая
   страница будет заменена.
7. `documents/eva/publish.md` — отдельное подтверждение публикации и проверка
   результата.
8. `documents/eva/rebind.md` — восстановить недоступную привязку, не меняя
   документ автоматически.
9. `documents/eva/errors.md` — отсутствует подключение, нет персонального токена,
   недостаточно прав, страница недоступна или изменилась; отдельно объяснить
   диалог **Перезаписать документ EVA?** при конфликте внешней версии.

Глава не содержит адресов API, общих токенов, выбора пространства и проверки
SSL: это административные настройки, недоступные обычному пользователю.

### 5.9 Экспорт, архив и удаление

1. `documents/export.md` — создание и скачивание только форматов, фактически
   доступных в текущем UI; основной пользовательский путь — Markdown и HTML для
   EVA.
2. `documents/archive.md` — действие **В архив**, диалог **Архивировать
   документ?**, состояние **В архиве** и последствия для редактирования.
3. `documents/delete.md` — безвозвратное удаление документа, истории, заданий и
   файлов экспорта; действие только для расширенного модератора и администратора.

Архивация и удаление описываются как разные операции.

### 5.10 Экран «Профиль»

1. `account/profile/open.md` — открыть настройки и перейти в **Профиль**.
2. `account/profile/name.md` — изменить значение поля **Имя** и обработать ошибку
   валидации.
3. `account/profile/avatar.md` — добавить или заменить **Аватар**.
4. `account/profile/timezone.md` — выбрать **Часовой пояс** и проверить
   сохранённое значение.
5. `account/profile/email.md` — посмотреть **Email**; пояснить, что после
   регистрации он не изменяется через профиль.
6. `account/profile/password.md` — из строки **Пароль** открыть форму, заполнить
   поля **Текущий пароль**, **Новый пароль** и **Подтвердите новый пароль**, затем
   проверить успешное сохранение. Выход из системы описывается отдельно: текущий
   интерфейс не обещает автоматическое завершение сессии после смены пароля.
7. `account/profile/eva-token.md` — в поле **EVA API токен** увидеть доступные
   EVA-подключения, состояние токена, добавить, заменить или удалить
   персональный токен.
8. `account/profile/eva-token-effects.md` — после удаления персонального токена
   чтение EVA остаётся возможным при наличии сервисного токена; без него чтение,
   сохранение черновика в EVA и публикация недоступны. Фоновая синхронизация всегда
   требует сервисный токен и не настраивается пользователем.

Значение EVA-токена после сохранения не показывается. Скриншоты и примеры не
должны содержать настоящий токен, пароль, рабочий адрес EVA или персональные
данные.

### 5.11 Отдельный экран выбора LLM

1. `account/chat-model.md` — открыть **Провайдеры моделей** и в поле **LLM**
   выбрать чат-модель из централизованно доступного списка.
2. `account/chat-model-impact.md` — объяснить только влияние на **Документы**:
   анализ и генерация используют выбранную в поле **LLM** модель по умолчанию.
   Эффекты настройки в других разделах RAGFlow находятся вне границ руководства.
3. `account/chat-model-errors.md` — модель отсутствует, недоступна или не
   сохраняется; какие сведения передать администратору.

Экран выбора модели — не часть формы **Профиль**. Для обычного пользователя он
не описывает добавление провайдера, API-ключи, URL, embedding, rerank, ASR, TTS,
VLM и системные модели. Эти элементы доступны только администратору и находятся
вне данного руководства.

Текущую подсказку поля **LLM** нельзя цитировать как полное описание влияния:
она упоминает новые базы знаний, тогда как раздел **Документы** также использует
настроенную чат-модель по умолчанию.

### 5.12 Действия оболочки настроек

1. `account/theme.md` — переключить светлую или тёмную тему.
2. `account/logout.md` — завершить свою пользовательскую сессию.

Тема и выход не являются полями профиля. Руководство не расширяет эти страницы
до управления оформлением продукта, активными сессиями других пользователей или
политиками аутентификации.
Переключатель темы отображается значками солнца и луны без текстового названия:
не следует придумывать для него подпись кнопки. **Выйти** — точная подпись
действия завершения сессии.

### 5.13 Помощь

1. `help/action-not-visible.md` — действие скрыто из-за роли, владельца, состояния
   документа или отсутствующей EVA-возможности.
2. `help/statuses.md` — пользовательский словарь состояний документа, операции и
   EVA-изменения.
3. `help/conflicts.md` — конфликт версии, повторная загрузка и защита от
   дублирования действия.
4. `help/report-problem.md` — время, документ, видимое состояние, действие, текст
   и код ошибки; не передавать пароль или токен.
5. `glossary.md` — документ бизнес-требований, ревизия, обсуждение, предложение,
   владелец, привязка к EVA, черновик в EVA и публикация.

## 6. Зафиксированный контур учётной записи

Обычный пользователь — аутентифицированный пользователь без признака
суперпользователя. Для него руководство описывает только следующий контур:

| Поверхность | Тип | Доступные действия |
| --- | --- | --- |
| **Профиль** | Отдельный экран | **Имя**, **Аватар**, **Часовой пояс**, просмотр **Email**, **Пароль**, **EVA API токен** |
| **Провайдеры моделей** | Отдельный ограниченный экран | Выбор LLM (чат-модели) по умолчанию |
| Тема | Действие оболочки настроек | Переключение светлой и тёмной темы |
| **Выйти** | Действие оболочки настроек | Завершение своей пользовательской сессии |

Источники данных, каналы чата, MCP, команда и API не получают страниц в этом
руководстве. При прямом переходе в закрытую настройку обычный пользователь
возвращается в **Профиль**. Это ожидаемое ограничение, а не инструкция искать
обходной путь.

## 7. Шаблон практической страницы

```text
# Результат действия

Кому доступно: роль, владение документом и нужное состояние
Перед началом: обязательные данные или доступная настройка учётной записи
Результат: проверяемый итог

## Выполнить
Нумерованные шаги с точными названиями элементов русского UI.

## Проверить результат
Новое состояние, ревизия, файл или подтверждение EVA.

## Если действие недоступно
Роль / владелец / состояние / доступная настройка учётной записи → следующий шаг.

## Если произошла ошибка
Безопасный повтор либо сведения для администратора без секретов.

Проверено для: версия, дата, роль и тип тестового окружения.
```

На странице показываются только действия заявленной роли. Условные варианты для
других ролей выносятся в короткую таблицу, а не смешиваются в один список шагов.

## 8. Карта скриншотов

Скриншот добавляется только там, где расположение элементов, состояние или
последствие решения трудно передать текстом. Один снимок принадлежит одной
странице руководства; остальные страницы ссылаются на неё и не копируют файл.
Базовый комплект состоит из 22 обязательных снимков: 12 для основного цикла
**Документов**, 6 для EVA и 4 для учётной записи. Ещё семь сценариев отмечены
как необязательные и не входят в критерий готовности первой версии.

### 8.1 Место снимка на странице

Используются три позиции:

1. **Ориентация** — после краткого результата и условий, перед шагами. Подходит
   для обзора экрана или новой рабочей области.
2. **Точка решения** — непосредственно перед шагом с выбором, подтверждением или
   необратимым действием.
3. **Проверка результата** — в разделе **Проверить результат** после шагов.

Нельзя помещать снимок до заголовка страницы, между предупреждением и
разрушающим действием либо вместо описания ожидаемого результата.

### 8.6 Требования к захвату и хранению

- Использовать русский интерфейс, настольный viewport `1440×900`, масштаб 100%,
  светлую тему; тёмная тема нужна только для `ACC-X1B`.
- Использовать один согласованный набор синтетических документов, пользователей
  и EVA-страниц. Не снимать production и не рассчитывать на размытие секретов.
- Для ролевых отличий делать отдельный снимок только тогда, когда видимый элемент
  действительно меняется. Отсутствующую кнопку не дорисовывать стрелкой.
- Один снимок показывает одно действие или один проверяемый результат. Номерные
  выноски допустимы, но стрелки не должны закрывать подписи и состояния.
- У каждого изображения обязательны русский alt-текст, подпись, версия
  приложения, дата захвата и роль пользователя.
- Обрезать браузерную рамку и пустые области. Сохранять читаемость при ширине
  контента 960 пикселей; мелкий текст на снимке не заменяет инструкцию.
- Перед публикацией проверить, что на снимке нет адресов электронной почты,
  реальных имён, URL рабочей EVA, токенов, паролей и закрытого содержания
  документов.

Публикуемые файлы хранятся в:

```text
docs/user-guide-ru/assets/screenshots/
  documents/
  eva/
  account/
  manifest.yaml
```

Имя файла начинается с ID, например
`documents/DOC-07-review-workspace.png`. В `manifest.yaml` для каждого ID
фиксируются владеющая страница, commit или версия интерфейса, дата, роль,
viewport и контрольная сумма. Исходные необработанные снимки с потенциально
чувствительными данными в репозиторий не добавляются.

## 9. Очерёдность написания

### P0 — основной пользовательский маршрут

- главная страница, открытие раздела и роли;
- список с фильтрами **Мои** и **Все**;

- переключение темы и выход;

## 10. Критерии готовности

Страница готова к публикации, когда:

- относится к разделу **Документы** или зафиксированному контуру учётной записи;
- проходит условия включения из раздела 1.2 и не превращает зависимость в новую
  главу;
- решает одну ясную пользовательскую задачу;
- проверена в текущем русском UI под каждой указанной ролью;
- названия кнопок и состояний совпадают с интерфейсом;
- при первом упоминании объект назван документом бизнес-требований, а точные
  подписи **Рабочие документы** и **Сохранённые документы** используются только
  для соответствующих областей интерфейса;
- термины и различия действия, процесса и состояния соответствуют разделу 2;
- не обещает действие, скрытое для роли или запрещённое состоянием;
- различает принятие предложения, применение изменений и новую ревизию;
- различает привязку, чтение, подготовку и публикацию в EVA;
- содержит ожидаемый результат и безопасную обработку применимой ошибки;
- не раскрывает секреты и персональные данные;
- использует только назначенные этой странице ID снимков из раздела 8;
- каждый обязательный снимок имеет актуальную запись в `manifest.yaml`, alt-текст
  и подпись, а необязательный снимок действительно добавляет информацию;
- указывает версию и дату проверки;
- все ссылки и изображения открываются.

## 11. Проверка руководства перед выпуском

1. Пройти основной путь под автором-создателем.
2. Проверить назначенный документ под автором-редактором.
3. Проверить чужой документ под модератором-создателем.
4. Проверить смену владельца и удаление под расширенным модератором.
5. Проверить профиль обычного пользователя: **Имя**, **Аватар**, **Часовой
   пояс**, **Email**, **Пароль** и весь жизненный цикл персонального EVA-токена.
6. Проверить, что в **Провайдерах моделей** обычному пользователю показывается
   только поле **LLM**, а настройка провайдеров ему недоступна.
7. Отдельно проверить, что расширенный модератор **Документов** без признака
   суперпользователя не получает административные настройки.
8. Проверить переключение темы и выход как действия оболочки, а не поля профиля.
9. Проверить EVA-сценарии на отдельном тестовом контуре без записи в реальные
   документы бизнес-требований.
10. Проверить внутренние ссылки, изображения и сборку сайта документации.
11. Выполнить редакторский поиск посторонних продуктовых разделов и
   администраторских инструкций.
12. Сверить каждый опубликованный снимок с указанными ролью и состоянием,
    проверить читаемость при ширине контента 960 пикселей и отсутствие секретов.
13. Сверить файлы с `manifest.yaml`: не должно быть пропущенных обязательных,
    дублирующихся или неиспользуемых снимков.
14. Сравнить все выделенные названия элементов с текущими русскими строками UI;
    отдельно проверить **Рабочие документы**, **Сохранённые документы**,
    **Обсуждение**, **Применить исправления**, **LLM** и EVA-подписи.
15. Убедиться, что внутренние названия компонентов, API-команд и состояний не
    попали в пользовательский текст.

Если роль или тестовый EVA-контур недоступны, соответствующая страница получает
статус `INCOMPLETE` и не публикуется как проверенная.

## 12. Размещение

Целевую документацию рекомендуется хранить в отдельном локальном дереве:

```text
docs/user-guide-ru/
  index.md
  start/
  documents/
    eva/
  account/
    profile/
    chat-model.md
    chat-model-impact.md
    chat-model-errors.md
    theme.md
    logout.md
  assets/
    screenshots/
      documents/
      eva/
      account/
      manifest.yaml
  help/
  glossary.md
```

Такое размещение отделяет локальное руководство от upstream-руководств по всему
RAGFlow. В Docusaurus подключаются только написанные и проверенные страницы;
пустые элементы будущего оглавления не публикуются.

## 13. Решение ревью, происхождение и применимые правила

Решение: структура пригодна как зафиксированная основа для написания отдельных
страниц. Готовым пользовательским руководством она не является.

В ходе ревью устранены следующие неоднозначности:

- основным названием объекта закреплён термин «документ бизнес-требований»;
- роль в **Документах** отделена от признака суперпользователя;
- экран **Профиль** отделён от поля **LLM**, темы и выхода;
- пользовательские EVA-операции отделены от настройки EVA-коннектора;
- удалено неподтверждённое ожидание автоматического выхода после смены пароля;
- первая версия ограничена русским настольным веб-интерфейсом;
- для обязательных и необязательных снимков назначены владеющие страницы,
  позиции, роли, состояния и правила хранения.

Классификация: `extension`. Документ отсутствует в подтверждённой upstream-базе
и описывает информационную архитектуру локального руководства. Код приложения и
публичная навигация документации не изменяются.

Применимы UPG-03 и TEST-01. В рамках ревью границы сверены с маршрутами и
политикой доступа настроек, серверной матрицей ролей **Документов**, полями
профиля, EVA-учётными данными и ограниченным режимом выбора модели. Матрица
ролей и политика маршрутов подтверждены узкими автоматическими тестами. Ревью
терминов дополнительно выполнено по текущим русским строкам и компонентам
интерфейса. Ревью не подтверждает работу полных пользовательских сценариев в
live-среде; такая проверка остаётся обязательным условием публикации инструкций.
