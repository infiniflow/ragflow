# Непрерывная очистка кода и упрощение алгоритмов

Дата: 2026-09-05. Статус: проект автоматизации и инструкция для работы агента. Runners, новые gates и автоматические исправления пока не внедрены. В этом изменении выполнена только пробная диагностика сложности двух Python-файлов; код приложения не изменялся.

Основание: [архитектура расширений](architecture-and-code-quality-ru.md), [переход T0–T7](architecture-transition-ru.md), [каталог правил](architecture-checks-ru.md). Документ уточняет DEAD-01/02 и вводит DEAD-03, SIMP-01/02/03. Он не разрешает массовое удаление стандартного ядра или изменение работающих продуктовых контрактов.

## 1. Рабочий цикл

При разработке агент выполняет цикл: **изменение → анализ затронутого модуля и потребителей → доказательства → небольшой patch → проверки → повторный анализ**. Подтверждённая очистка внутри согласованной задачи выполняется вместе с ней без отдельного запроса разрешения. Сомнение в использовании не превращается в автоматическое удаление.

Автоматизируются обнаружение, сбор доказательств, выбор проверок, подготовка допустимых исправлений и повторная проверка. Часть изменений агент способен выполнить самостоятельно; технический gate проверяет результат. Семантическую эквивалентность произвольного алгоритма статические метрики и успешные тесты сами по себе не гарантируют.

| Момент | Область | Действие |
| --- | --- | --- |
| Начало задачи | Рабочий diff, владелец, upstream-происхождение, текущие consumers | Зафиксировать снимок и исходные findings; отделить старое от появившегося в задаче |
| После законченного изменения | Изменённые symbols, целый модуль, обратные зависимости и регистрации | Найти новые unused symbols, освобождённые helpers и рост сложности |
| Перед завершением задачи | Весь связанный сценарий и его контракты | Применить доказанную очистку, проверить поведение, удалить собственные дубли |
| Pre-commit | Быстрые проверки выбранных файлов | Показать findings; не запускать семантическое переписывание в hook |
| PR/CI | Полный граф нужного профиля плюс базовая ветка | Только проверка: не менять исходники, не stage/commit/push и не расширять baseline |
| Плановый полный CI и upstream update | Все собственные модули и поддерживаемые интеграции | Найти каскадно освободившийся код, пересмотреть локальные исправления ядра и hotspots |

Плановый CI здесь — часть проекта, не созданное расписание. Автоматическая очистка не означает автоматический merge или деплой.

## 2. Что считать мёртвым кодом

Отдельно учитываются неиспользуемое имя, недостижимый исполняемый путь, неподдерживаемая продуктовая функция, дублирующий алгоритм и лишняя абстракция. Это разные основания для изменения.

Рабочий граф содержит symbols/files и следующие рёбра: imports/re-exports, вызовы/передача callback, чтение данных/типов, registry/DSL references, templates/assets, build/runtime configuration. Множество корней — все поддерживаемые HTTP/SDK/MCP/CLI/worker входы, публичные экспорты и динамические реестры данного профиля.

Статический кандидат на удаление — собственный symbol, недостижимый от этих корней. Дополнительно проверяется, что он не является внешним контрактом и что неопределённые динамические вызовы не могут его использовать. «Корни полны» — проверяемая предпосылка для конкретного профиля, а не предположение анализатора.

В RAGFlow обычного поиска импортов недостаточно:

- [api/apps/__init__.py](../../api/apps/__init__.py) находит маршруты по именам файлов и загружает их через `spec_from_file_location`.
- [agent/component/__init__.py](../../agent/component/__init__.py) импортирует модули, извлекает классы и находит компоненты по строковому имени.
- [web/src/routes.tsx](../../web/src/routes.tsx) содержит lazy imports страниц.
- Сохранённые DSL, job types, миграции и нативные профили могут ссылаться на код без обычного вызова в исходнике.

Tests входят в отдельный граф проверки. Вызов только тестом не делает runtime-функцию нужной продукту; при этом test helper или тест публичного SDK имеет самостоятельное назначение. Нулевое coverage и отсутствие наблюдённых вызовов — лишь сигналы для поиска, не доказательство мёртвого кода.

### Сбор доказательств

1. Проверить происхождение по принятой upstream-базе. `unclassified` не допускается к автоматическому удалению.
2. Получить findings от Ruff/Vulture, TypeScript/Knip и Go-проверок с закреплёнными версиями и профилями из архитектурного документа. Анализ одного изменённого файла не доказывает отсутствие внешнего потребителя.
3. Раскрыть references и регистрации, включая строки в конфигурации, шаблонах, тестах и упаковке. Неразрешимый `getattr`/reflection/dynamic import сохраняется как неизвестное ребро и препятствует удалению потенциальной цели.
4. Проверить поддерживаемые API/SDK, persisted DSL и upgrade paths. Для публичного символа предполагается внешний потребитель, пока контракт не подтверждает обратное.
5. Проверить побочные эффекты объявления/импорта: decorators, class body, default arguments, annotations, module initialization, Go init/blank imports, side-effect imports JS.
6. Определить проверяемый patch и минимальный набор тестов/сборок, которые затрагивает удаление. Не удалять тест актуального поведения только потому, что он мешает исправлению.

## 3. Какие удаления выполняются автоматически

Режим задаётся находке, а не глобальному проценту confidence. Число анализатора не является вероятностью безопасности изменения.

| Режим | Примеры | Действие агента |
| --- | --- | --- |
| `AUTO_LOCAL` | Локальное неиспользуемое связывание с доказанно чистым литеральным RHS; лишний type-only import без изменения доступного type contract | Узкий whitelist преобразований, проверка scope/effects, patch и обязательная верификация |
| `AUTO_VERIFIED` | Собственный приватный helper/module без потребителей, динамики, внешнего контракта и эффектов загрузки | Полный пакет доказательств достижимости; удалить код и освободившиеся собственные references; проверить модуль и потребителей |
| `REVIEW_REQUIRED` | Публичный export, компонент DSL, маршрут, worker type, зависимость пакета, миграция, импорт для регистрации | Установить контракт/продуктовый смысл и подготовить конкретное изменение; до этого не удалять |
| `PRESERVE` | Активный consumer, поддерживаемый upstream-профиль, нужная миграция, регистрационный side effect | Сохранить; уточнить entrypoint либо описание использования |
| `INCOMPLETE` | Неизвестное происхождение, неполные refs, недоступные данные/профиль, отсутствующий анализатор | Не применять patch; указать конкретное недостающее доказательство |

`REVIEW_REQUIRED` означает предметный разбор, а не обязательный вопрос пользователю о каждом helper. Агент продолжает его самостоятельно в пределах задачи. Решение о прекращении поддерживаемой пользовательской функции не выводится из метрики unused: для него нужно продуктовое основание в согласованной задаче.

### Ограничения механической очистки

- Удаление имени не равно удалению вычисления. Из `unused = send_event()` нельзя получить пустое место. Даже замена на `send_event()` может менять время жизни возвращённого ресурса; нужна проверка эффектов.
- Нельзя удалять import только по F401: в приложении он может регистрировать компоненты. Особенности экспортов и исправлений `__init__.py` отдельно описаны в [Ruff F401](https://docs.astral.sh/ruff/rules/unused-import/).
- Ruff помечает fix F841 как unsafe; политика проекта не включает массовый `--unsafe-fixes`. Для переменной проверяются RHS, комментарии и scope. См. [Ruff F841](https://docs.astral.sh/ruff/rules/unused-variable/).
- Недостижимое присваивание всё ещё может влиять на область видимости Python; недостижимый `yield` — на тип функции. AST/symbol-table и контракт должны сохраняться, иначе это не `AUTO_LOCAL`.
- `locals`, `globals`, `eval`, `exec`, reflection и изменение namespace могут делать формально unused имя наблюдаемым. Неразрешённая динамика исключает механическое удаление связывания даже с литеральным RHS.
- Нельзя автоматически убирать публичные аргументы, type declarations, struct fields или enum values: они могут определять сериализацию и внешние контракты.
- «Закомментированный код» определяется предметно: примеры, лицензии и объяснение инварианта не удаляются текстовой регуляркой.
- Удаление зависимости выполняется после проверки импорта, бинарных entrypoints, build scripts, ресурсов и всех поддерживаемых install-профилей. Общая upstream-зависимость не удаляется по анализу только расширения.

Небольшой `AUTO_VERIFIED` patch можно применить без дополнительного запроса пользователю, если доказательства собраны в рамках уже согласованной разработки. Изменения за её пределами остаются отдельными findings, а не расширяют задачу скрыто.

## 4. Протокол автоматического patch

1. Зафиксировать fingerprint текущих затрагиваемых файлов, содержимое до patch и базовые результаты. Не путать этот снимок с Git HEAD: в дереве могут быть чужие незакоммиченные изменения.
2. Сформировать один смысловой набор изменений, проверить допустимость режима и отсутствие новых edits с момента анализа. При расхождении fingerprint остановить применение и пересчитать доказательства.
3. Применить AST-aware преобразование либо точечный patch. Не удалять каталоги по вычисленным маскам и не применять project-wide autofix.
4. Запустить формат/lint, type/build checks, тесты поведения и registry/contracts по selector. Для удалённого runtime-пути убедиться, что список входов изменился только ожидаемым образом.
5. При регрессе убрать только собственный patch, если его preimage/postimage по-прежнему известны. При конкурирующих edits не использовать `reset --hard`, общий restore или перезапись файла старой копией: заново согласовать изменения по содержимому.
6. При успехе пересчитать достижимость. Удаление вызывающей функции может сделать мёртвым helper; каждое следующее удаление проходит тот же цикл доказательств.
7. Завершить на неподвижной точке либо при недостатке доказательств/выходе за объём задачи. После трёх безрезультатных попыток одного преобразования перейти к диагностике, а не запускать бесконечные исправления.

Состояния находки: `DETECTED → CLASSIFIED → EVIDENCED → PATCHED → VERIFIED`; отдельные исходы `PRESERVED`, `REVIEW_REQUIRED`, `INCOMPLETE`, `REVERTED`. Статус `VERIFIED` ставится только по фактическому результату, не по факту исчезновения предупреждения.

Предлагаемое место реализации — режимы существующего проектируемого `tools/quality/check_architecture.py`: `scan`, `plan`, `apply`, `verify`. Это будущий CLI-контракт, а не готовые команды. `scan/plan` не пишут исходники; `apply` доступен только локальному исполнителю в явном режиме; CI использует `scan/verify`. Автоприменение по умолчанию выключено до приёмки на T2–T3.

## 5. Как выявлять излишнюю сложность

Разделять сложность понимания, вычислительную стоимость и сложность обязательных бизнес-правил. Длинный switch может быть правильным диспетчером, а короткая функция — скрывать N+1 запросов. Количество строк не является целевой функцией оптимизации.

| Сигнал | Как измерять | Что проверять предметно |
| --- | --- | --- |
| Ветвление | McCabe/C901 для Python; complexity для JS/TS; согласованный Go-анализатор | Переплетены ли независимые сценарии, повторяются ли условия |
| Вложенность | AST depth условных блоков и циклов | Можно ли выразить предусловия явно и убрать вложенные состояния |
| Объём функции | Executable statements/lines без комментариев и декларативных assets | Несколько ли причин изменения; не является ли функция таблицей данных |
| Связанность | Число внешних зависимостей и пересечений слоёв | Смешаны ли SQL, права, prompt, retry и транспорт |
| Повторные проходы | Циклы, поиск внутри цикла, повторная сортировка/парсинг | Может ли индекс/одно вычисление убрать лишнюю работу |
| I/O amplification | DB/API calls на операцию и размер входа | N+1, повторные fetch, ненужные round trips |
| Рост памяти/времени | Замеры на возрастающих размерах входа | Копии больших данных, неограниченный fan-out, плохая структура данных |
| Повторение правила | Сходство AST как сигнал плюс анализ смысла | Можно ли дать правилу одного владельца без универсального framework |
| Изменяемое состояние | Число флагов, состояний и мест мутации | Невозможные комбинации, неявный порядок действий, двойное хранение derived state |

В Python использовать существующий Ruff с явно включённым [C901](https://docs.astral.sh/ruff/rules/complex-structure/). Во frontend — правила ESLint [complexity](https://eslint.org/docs/latest/rules/complexity) и [max-depth](https://eslint.org/docs/latest/rules/max-depth), проверив поддержку закреплённой версией. Для Go выбрать и закрепить анализатор на T2 с проверкой native-профилей. Не вводить самописную «когнитивную сложность» без определения и приёмочных fixtures.

Метрики разных языков/инструментов могут по-разному считать выражения. Сравнивать до/после нужно одной версией, конфигурацией и профилем; межъязыкового рейтинга по одному числу не строить.

### Первичные пороги для калибровки

Это проектные сигналы, не отраслевой стандарт и не уже включённые gates:

- McCabe > 10, вложенность > 3 или > 80 исполняемых строк — кандидат на разбор изменяемой собственной функции.
- McCabe > 15, вложенность > 4 либо рост McCabe на 3 и более — обязательное объяснение в задаче: упрощение или аргумент, почему сложность выражает нужные правила.
- Повторение одной бизнес-проверки в двух владельцах и подтверждённый N+1 — повод для разбора независимо от длины функции.
- Старая функция с большим числом ветвей не блокирует несвязанную задачу. Новое превышение или изменение самой функции требует разбора. Upstream-код оценивается как hotspot интеграции, без автоматического рефакторинга.

После исходного измерения пороги калибруются по характеру собственных модулей. Не ослаблять порог в том же patch ради конкретного предупреждения. Gate SIMP-01 блокирует отсутствие разбора значимого сигнала, а не любое число > 15. Если упрощение не улучшает понятность или вводит больше сущностей, допустимо сохранить алгоритм с кратким предметным обоснованием и тестами.

Приоритет работ: сначала новые проблемы в затронутом сценарии; затем подтверждённые hotspots по профилю и I/O; затем старый долг по частоте изменений. Все существующие сложные функции не становятся задачей текущего PR.

## 6. Протокол упрощения алгоритма

### Зафиксировать контракт

До изменения записать входы, выходы, ошибки и их приоритет, порядок и кратность side effects, ограничения памяти/времени, tenant scope, транзакцию, retry/cancel и публичный формат. Неверное текущее поведение не объявляется эталоном: его исправление выделяется явно и проверяется по требованию.

### Выбрать минимальное преобразование

| Проблема | Предпочтительное действие | Что обязательно сохранить |
| --- | --- | --- |
| Глубокие независимые проверки | Guard clauses и именованные предикаты | Порядок ошибок, short-circuit и отсутствие лишних вызовов |
| Смешение команд | Небольшие обработчики сценариев внутри владельца | Общие предусловия до dispatch, транзакция, неизвестная команда |
| Повторный поиск по списку | Индекс по ключу, если он соответствует контракту | Дубликаты, порядок, hashability и память |
| Повторный дорогой parse/расчёт | Один расчёт в пределах операции | Зависимость результата от изменяемого состояния |
| N+1 | Batch-fetch/query или согласованный предрасчёт | Tenant filters, pagination, consistency, лимит batch |
| Много связанных флагов | Явное состояние и разрешённые переходы | Реально допустимые комбинации, восстановление, persisted формат |
| Обёртка без полезной границы | Удалить и перенести вызов к владельцу | Настоящие адаптеры к upstream и права доступа |

Не заменять линейный поиск set/dict автоматически: дубликаты, порядок и дополнительная память могут быть частью контракта. Не превращать 15 ветвей в 15 классов ради показателя. При разбиении функции оценивать число переходов между helpers, суммарные решения сценария и количество новых публичных сущностей, а не только максимальный C901.

### Доказать сохранение поведения

1. Выполнить целевые тесты до изменения. Если исходный сбой затрагивает проверяемый контракт, локализовать его до вывода об эквивалентности.
2. Для чистого алгоритма применить differential tests на фиксированных и генерируемых входах: пустые значения, дубликаты, границы, ошибки, порядок и determinism. Зафиксировать seed. Сравнивать с требованием и эталонным результатом; старая реализация сама может содержать ошибку.
3. Для I/O сравнивать не только return, но и записи/события, их кратность, ошибки, транзакционные эффекты и cancel/retry. Использовать изолированные fixtures; не запускать старый и новый пути против рабочей БД для «сравнения».
4. При изменении правил ревизий/очереди выполнить реальные конкурентные тесты. Unit fake не доказывает atomicity.
5. Эталон до изменения брать из сохранённого снимка в одноразовом test harness; не оставлять две production-реализации. После сравнения сохранять независимые tests на ожидаемое поведение, а не копию старого кода.

Для floats, недетерминированных результатов и сортировок явно определить допустимость расхождений до теста. Нельзя сортировать выходы или ослаблять допуск после изменения, чтобы спрятать регресс. Для LLM фиксируются модель/prompt/dataset и eval; равенство текста не является универсальным критерием качества.

### Проверить цену упрощения

Для изменений алгоритма, I/O или структуры данных измерять до/после на одном окружении. Использовать минимум три размера входа в пределах реального контракта: например N, 2N, 4N, включая близкий к верхней границе. Отдельно учитывать прогрев/cache, peak memory, число запросов и ошибок. Такие измерения подтверждают поведение в выбранном диапазоне, но не доказывают асимптотику для любых N.

Для чистого microbenchmark выполнить несколько повторных серий после прогрева, записать разброс и median. Предварительное правило: воспроизводимое ухудшение времени или peak memory более чем на 10% сверх измеренного шума требует разбора; жёсткий ресурсный лимит сценария имеет приоритет независимо от процента. Порог конкретного benchmark задаётся до изменения. Для latency сервиса p95 рассчитывать только по достаточной серии запросов, сохраняя sample count; не вычислять содержательный p95 по пяти запускам.

Если упрощение делает алгоритм понятнее ценой допустимой памяти/времени, это явный tradeoff с результатами, а не скрытый регресс. Для небольшого изменения управляющей структуры без влияния на I/O/обход данных отдельный benchmark не обязателен; достаточно объяснения неприменимости и целевых тестов.

### Критерий принятия

Поведение соответствует контракту, новые нарушения отсутствуют, ресурсные ограничения соблюдены и причина сложности устранена либо стала явно выраженной. Меньшее число строк или ветвей без этих условий не считается улучшением.

## 7. Пробная диагностика текущего кода

2026-09-05 выполнено без исправления файлов, Ruff 0.15.5:

```text
ruff check --select C901 --config lint.mccabe.max-complexity=15 --output-format json api/apps/business_documents/service.py api/apps/business_documents/worker.py
```

Одна находка: `_dispatch` в [service.py](../../api/apps/business_documents/service.py), строка 852 на момент измерения, McCabe 23 > 15. В `worker.py` этим правилом превышений данного порога не найдено. Это не оценка всей сложности или качества этих файлов и не аудит всего репозитория.

В просмотренном `_dispatch` ветви выбирают команды и проверяют lifecycle, открытые вопросы, текущую оценку, revision и формат экспорта. Поэтому автоматическое превращение функции в lookup table без анализа неправильно: общая проверка archived, порядок отказов и вызовы `_request_job` должны сохраниться.

Кандидат на дальнейший разбор: отделить предусловия отдельных команд в небольшие обработчики у того же владельца, если это улучшит чтение. До изменения проверить все команды, unknown command, archived state, конфликт ревизии и отсутствие записи при отказе; после — тот же контракт и транзакционные тесты. Если результат лишь рассеивает ветви по helpers, сохранить текущий dispatcher с обоснованием. В этом проектировании функция не переписана.

## 8. Доказательства и CI

Для каждой применённой очистки сохранить: rule ID, origin, symbol/fingerprint, причина недостижимости или сложности, покрытые корни/профили, неизвестные рёбра, режим действия, patch fingerprint, выполненные checks и before/after результат. Для алгоритма дополнительно — контракт, change rationale, metrics, differential cases и performance evidence при применимости.

Успешные небольшие операции входят в общий отчёт задачи, не требуют отдельного постоянного реестра на каждый удалённый import. Неразобранные findings и исключения используют существующий проект baseline; новый параллельный debt tracker не создаётся.

В CI новые достоверные dead-code findings в собственной области блокируют задачу согласно DEAD-01. Неопределённая динамическая находка требует разбора области анализа, но не допускает удаления ради зелёного статуса. Неполнота обязательной проверки возвращает `INCOMPLETE`; подтверждённый сохранённый entrypoint устраняет ложную находку проверяемой конфигурацией.

SIMP-01 проверяет наличие содержательного разбора новых значимых сигналов; смысл обоснования проверяется ревьюером. SIMP-02 проверяет выполнение применимых before/after tests и benchmarks; вывод об эквивалентности остаётся ограниченным их покрытием. SIMP-03 запрещает скрывать сложность переносом, отключением правила или расширением baseline без основания.

## 9. Приёмочные пробы автоматизации

| Проба | Ожидаемый результат |
| --- | --- |
| Приватный чистый helper перестал иметь потребителей после текущей правки | AUTO_VERIFIED после полного анализа корней; удаление и тесты |
| Две приватные функции вызывают только друг друга и не имеют входящего пути | Кандидат всей недостижимой группы; нельзя сохранить её только из-за внутренних вызовов |
| Компонент доступен по строке persisted DSL | PRESERVE либо INCOMPLETE без доступа к инвентаризации; не удалять |
| Unused import выполняет регистрацию | PRESERVE; добавить проверяемое описание entrypoint |
| Unused assignment вызывает I/O или держит ресурс | Не AUTO_LOCAL; эффекты должны сохраниться |
| Недостижимое присваивание меняет local binding или есть yield | Не удалять по одной control-flow находке |
| Public SDK export не используется внутри repo | REVIEW_REQUIRED; внешний контракт не считается мёртвым |
| После анализа файл изменил другой исполнитель | Fingerprint mismatch; patch не применяется |
| После удаления регресс, в файле нет чужих новых изменений | Откат только собственного patch; REVERTED |
| Сложность снизилась после переноса ветвей в безымянные helpers | SIMP-03: метрика сама по себе не подтверждает упрощение |
| Замена списка set потеряла порядок/дубликаты | Differential test FAIL; изменение не принимается |
| Batch-query потерял tenant filter | DATA-01 FAIL независимо от ускорения |
| N+1 устранён, outputs/effects сохранены, DB calls уменьшились | Проверяемое упрощение с измеренным улучшением |
| C901 снизился, но peak memory нарушил лимит | SIMP-02 FAIL |
| Анализатор или benchmark не выполнился | INCOMPLETE для применимой проверки, не PASS |
| Dispatcher выше порога выражает обязательные команды и имеет ясные границы | Допускается оставить после содержательного разбора и проверки контракта |

Внедрение следует T2–T3: сначала scan и evidence, затем негативные fixtures и блокирующие checks; автоприменение включается только для принятых whitelist-преобразований. Семантическое упрощение выполняется агентом отдельными проверяемыми patch в рамках T4–T5 и дальнейшей разработки.
