# Уникальные названия и привязка документов к EVA Wiki

## Требования и инварианты

1. Название бизнес-документа уникально во всей системе после NFKC-нормализации,
   удаления краевых пробелов, схлопывания пробельных последовательностей и
   регистронезависимого сравнения.
2. При создании документа UI использует контракт `create_document.v2`.
3. Если в настроенном для Documents пространстве EVA Wiki есть доступные страницы
   с тем же нормализованным названием, документ не создаётся до явного решения
   пользователя: выбрать страницу или продолжить без привязки.
4. Для каждого совпадения показываются кликабельные хлебные крошки страницы.
5. Одна EVA-страница может быть привязана только к одному бизнес-документу.
6. Привязка требует отдельного подтверждения: пользователь должен увидеть, что
   при последующей публикации содержимое EVA-страницы будет полностью заменено
   содержимым документа. Сама привязка страницу не изменяет.

## Архитектура и границы

```text
Create form
  -> POST create_document.v2
     -> проверка доступа к источникам
     -> проверка уникальности title_key
     -> EVA adapter: точный поиск по названию
        -> 0 совпадений: создать документ
        -> 1..N: 409 EVA_BINDING_DECISION_REQUIRED
              -> UI показывает иерархию и ссылки
              -> SKIP: повторить создание без привязки
              -> BIND: показать подтверждение замены
                    -> повторить с page_url + confirm_replace=true
     -> транзакция: document + EVA binding + creation event
```

- `business_documents/domain/names.py` владеет чистой нормализацией названий.
- `common/data_source/eva_wiki_connector.py` отвечает только за чтение страниц и
  построение их иерархии из EVA.
- `api/apps/business_documents/eva_changes.py` выбирает настроенный коннектор и
  переводит внешние ошибки в ошибки сценария.
- `api/apps/business_documents/service.py` оркестрирует решение пользователя и
  транзакцию создания.
- `api/db/db_models.py` обеспечивает окончательные конкурентные гарантии БД.
- `web/src/pages/business-documents/index.tsx` показывает предложение и получает
  явное подтверждение; решение не выводится из состояния UI неявно.

## Хранение и конкурентные гарантии

- `business_document.title_key` — SHA-256 нормализованного названия с уникальным
  индексом. Предварительная проверка даёт понятную ошибку, индекс закрывает гонку.
- `business_document_eva_binding` — текущая проекция привязки: одна строка на
  документ, уникальные хеши канонического URL и EVA identity
  (`origin + project_id + document_id`).
- Создание документа, привязки и события выполняется в одной транзакции.
- Миграция вычисляет `title_key`, останавливается при уже существующих дублях и
  переносит старые event-backed EVA-привязки в уникальную проекцию. Конфликтные
  старые привязки требуют ручного разрешения до запуска новой версии.

## API

Первый запрос не содержит решения по EVA. При совпадениях сервер возвращает
`409 EVA_BINDING_DECISION_REQUIRED` и `details.matches` с иерархией, ссылками и
признаком доступности привязки.

Повторный запрос содержит одно из решений:

- `eva_decision: {"mode": "SKIP"}`;
- `eva_page_url` и
  `eva_decision: {"mode": "BIND", "confirm_replace": true}`.

Перед BIND сервер повторно разрешает страницу, проверяет её доступность и название.
Это защищает от устаревшего выбора и обхода UI. Контракт v1 сохранён для создания
документов без EVA-привязки; переданный в v1 `eva_page_url` отклоняется с
`EVA_BINDING_REQUIRES_SCHEMA_V2`, поскольку безопасная привязка требует v2 и
явного `confirm_replace=true`.

## Разбиение работ

### T1. Каноническое уникальное название

- Граница: pure-domain функция, поле/индекс, миграция, конфликт API.
- DoR: согласована глобальная область уникальности и правило нормализации.
- DoD: эквивалентные Unicode/case/whitespace варианты конфликтуют; гонку закрывает
  индекс; миграция диагностирует старые дубли.

### T2. Точный поиск EVA и иерархия

- Граница: read-only connector и application adapter, без изменения EVA.
- DoR: настроено пространство Documents и определён формат EVA URL.
- DoD: возвращаются все доступные точные совпадения, стабильный порядок,
  cycle-safe хлебные крошки и ссылки.

### T3. Решение и подтверждение в UI/API

- Граница: контракт v2, ответ-challenge, компактная плашка и диалог.
- DoR: утверждён текст предупреждения и различие между привязкой и публикацией.
- DoD: без решения запись не создаётся; BIND без `confirm_replace=true` отклоняется;
  SKIP создаёт документ без ссылки.

### T4. Эксклюзивная привязка

- Граница: отдельная текущая проекция, транзакционная запись и backfill.
- DoR: определена стабильная EVA identity и политика старых конфликтов.
- DoD: параллельные попытки привязать одну страницу не создают две связи;
  повторное подключение подчиняется тому же ограничению.

### T5. Проверка

- Граница: unit/component проверки без обращения к общей EVA или production БД.
- DoR: доступны локальные Python/Node зависимости.
- DoD: backend-сценарии, connector, UI, type-check, lint и форматирование проходят;
  живая интеграция с EVA и PostgreSQL остаётся отдельным release gate.

## KISS, YAGNI и эксплуатационные решения

- Используется один create endpoint с ответом-challenge, без отдельного preflight
  endpoint, временных reservation-токенов и кэша результатов.
- Поиск выполняется только при создании v2 и только в пространстве Documents.
- Нет фоновой синхронизации названий: после выбора сервер повторно проверяет
  выбранную страницу.
- Нет автоматической публикации или перезаписи EVA при привязке.
- Нет новой plugin-системы, outbox или распределённой блокировки: требуемые гонки
  закрываются транзакцией и уникальными индексами.

## Ограничения релизной проверки

Перед production-развёртыванием отдельно проверить миграцию на копии реальной БД,
наличие старых дублей названий/привязок и сценарий точного поиска с реальной EVA.
Непройденная живая проверка не считается успешной.
